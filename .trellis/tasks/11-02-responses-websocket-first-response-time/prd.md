# 修复 Responses WebSocket 首字时间漏记

## 目标

普通 Responses WebSocket 请求收到上游响应后，消费日志能记录并展示本轮真实的首响应时间，避免已经正常流式输出却显示“首字 不适用”

## 来源与背景

- 用户链路为“客户端 → new-api → codex-proxy-rs”
- 用户提供的消费记录截图中，流式请求有 Token、输出速度和总耗时，但首字均显示“不适用”
- 用户最初要求“新建一个 trellis 任务到 new-api，等会我去做”；2026-11-02 要求启动修复，并确认了首次完整 Brief
- 已在本地 new-api 提交 `67b342c179808f992202d59c63a4f74faf8aa99f` 复现普通 Responses WebSocket 的漏计时，详情见 [排查与复现证据](research/evidence.md)
- 截图本身不能区分 SSE 和 WebSocket，未读取截图对应的实际日志，不能将这几条记录断定为 WS 请求

## 范围与要求

- R1：普通 Responses WebSocket 收到首个上游响应事件时，记录当前 turn 的首响应时间；沿用首响应口径，`response.created` 即可触发，不必等待正文
- R2：每轮只记录一次，后续响应事件不覆盖首响应时间；同一连接上的下一轮独立计时
- R3：复用既有 RelayInfo 首响应事实和消费日志 `other.frt` 毫秒字段；没有上游响应时保留未知，不用总耗时或本地心跳补造首字
- R4：保持现有请求与响应透传、usage、预扣与结算、重试、SSE 和 Compact 的行为，改动限定在本问题所属边界

## 验收标准

- [x] AC1 / R1：新增正式回归用例，在旧实现中稳定失败；预设请求已开始 2 秒后处理 `response.created`，首响应应被记录，消费日志生成的 `frt` 为合理正值
- [x] AC2 / R2：首响应建立后，再处理正文增量等后续帧，记录的首响应时间保持不变
- [x] AC3 / R2：同一 WS 连接连续处理两个 turn，各轮使用自己的起点和首次响应，不继承上一轮时间
- [x] AC4 / R3：尚未收到上游响应的场景继续保持未观测状态，不伪造有效首字；Ping/Pong 等连接控制不被当作模型响应
- [x] AC5 / R3：正常完成请求的消费日志 `other.frt` 反映首响应而非完成时间，现有前端可直接展示；Token、总耗时、速率和费用保持原合同
- [x] AC6 / R4：相关普通 WS、SSE 与 Compact 既有回归通过，明确记录验证命令和仍未实测的集成范围

## 非目标

- 不修改 codex-proxy-rs
- 不调整前端对 `frt = 0` 的显示规则，也不通过放宽正数判断掩盖漏记
- 不新增计时字段、数据库迁移或第二套计时状态
- 不按总耗时、Token 速度或其他时间推算并回填历史首字
- 不扩展为 WS 选渠、重连、重放、计费或页面重构
