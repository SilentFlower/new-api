# GitHub 公共仓库 Key 泄露扫描技术设计

## 1. 设计目标

在不把完整用户令牌发送给第三方的前提下，使用 GitHub 公共代码搜索发现候选文件，在 new-api 服务器本地完成完整令牌精确比对，并通过站内通知与钉钉安全群推动处置。

本设计优先保证：

- 完整令牌、16 位搜索锚点和外部服务凭据不进入日志、数据库、任务状态或管理 API。
- 扫描只处理 GitHub 公共仓库结果，不读取或报告私有仓库。
- 调度复用现有 `system_task` 的主节点、互斥、租约和任务历史能力。
- 外部搜索、候选下载和通知失败不会阻塞 new-api 的正常转发请求。
- 所有新增持久化结构兼容 SQLite、MySQL 和 PostgreSQL。

## 2. 范围与边界

### 2.1 扫描对象

- 数据源为 `model.Token`，只读取未软删除记录的 `Key`。
- 启用令牌优先；禁用、耗尽和过期令牌低优先级补扫。
- 本地对候选文件搜索完整的 `Token.Key` 字节串。由于 `sk-<key>`、裸 `<key>` 与 `sk-<key>-<suffix>` 都包含该字节串，无需分别构造三种匹配表达式。

### 2.2 明确不覆盖

- GitHub 非默认分支、历史提交、已删除内容、未索引或超过搜索限制的文件。
- 被拆行、拼接、转义、加密或编码后不再包含连续明文的令牌。
- 私有仓库与其他代码托管平台。
- `model.Channel.Key` 等上游供应商凭据。

## 3. 总体数据流

```text
system_task 调度或管理员手动触发
  -> 枚举并排序未软删除 Token
  -> 在内存中计算 HMAC 指纹与稳定 16 位锚点
  -> GitHub 全站 Code Search（只发送锚点）
  -> 拒绝私有或可见性未知结果
  -> 下载公开候选内容（有界读取）
  -> 在内存中完整 Key 精确比对
  -> 幂等更新扫描状态与泄露位置
  -> 站内通知 root 管理员与令牌所属用户
  -> 首次/新位置推送钉钉并 @所有人
  -> 未处置结果每 7 天普通提醒
```

## 4. 配置与密钥

### 4.1 管理后台配置

新增独立的 operation setting 模块，提供：

- `token_leak_scan.enabled`：默认 `false`。
- `token_leak_scan.interval_hours`：默认 `24`，允许 `1`～`168`。

设置页只返回并展示以下环境配置状态，不返回值：

- GitHub 扫描凭据是否存在。
- HMAC 扫描密钥是否存在。
- 钉钉机器人 Webhook 凭据是否存在。
- 最近一次 GitHub 鉴权结果与时间。

### 4.2 环境变量

- `GITHUB_TOKEN_LEAK_SCAN_TOKEN`：独立 fine-grained PAT，无额外仓库权限。
- `GITHUB_TOKEN_LEAK_SCAN_SECRET`：至少 32 字节随机 HMAC 密钥。
- `DINGTALK_TOKEN_LEAK_WEBHOOK_TOKEN`：固定安全群自定义机器人 token。
- `DINGTALK_TOKEN_LEAK_WEBHOOK_SECRET`：机器人开启加签时使用；未配置时按机器人当前安全策略发送。

这些值只在进程环境中读取，不写入数据库，不通过 API 回显，也不进入命令参数、任务载荷或日志。

## 5. 稳定锚点与指纹

对完整 `Token.Key` 使用 HMAC-SHA256，并用不同域标签隔离用途：

- 指纹：`HMAC(secret, "fingerprint\x00" || key)` 的十六进制摘要。
- 窗口摘要：`HMAC(secret, "anchor\x00" || key)`。
- 偏移：把窗口摘要前 8 字节解释为无符号整数，再对 `len(key)-16+1` 取模。
- 锚点：从完整 Key 的偏移位置截取连续 16 个字符。

同一 HMAC 密钥下，同一令牌始终只暴露同一片段，避免周期扫描逐渐暴露更多字符。HMAC 密钥轮换会改变指纹和锚点，但泄露位置的幂等键不依赖指纹，因此不会重复创建同一位置记录。

内存中的完整 Key 与锚点只存在于单条扫描生命周期；任何错误对象不得包装请求 URL、Authorization 头或响应原文。

## 6. GitHub 搜索客户端

新增独立 GitHub 客户端，使用 `net/http` 与 `common` JSON 包装函数，不依赖本机 `gh` 登录态。

### 6.1 查询规则

- 使用经过 URL 编码的精确 16 位锚点查询。
- 不添加 `repo:`、`user:`、`org:` 等范围限定。
- 每页最多 100 条，最多读取 GitHub 可返回的 1000 条结果。
- `incomplete_results=true`、`total_count>1000` 或结果可见性缺失时，将该令牌标记为扫描不完整。
- `repository.private=true` 的候选直接丢弃，不下载、不持久化、不通知。

### 6.2 限流与失败处理

- 默认每分钟最多 8 次 Code Search HTTP 请求，分页请求逐次计入预算。
- 限流等待使用可响应 `context.Context` 的定时器，不增加新的全局常驻 ticker。
- 搜索、内容下载均设置连接和整体超时，并限制响应体大小。
- 对 429、GitHub 次级限流和可恢复 5xx 做有限重试，尊重 `Retry-After`；鉴权失败立即结束本轮任务。
- 候选下载受 GitHub 内容大小边界与本地读取上限双重保护。
- 错误只映射为稳定的脱敏代码，例如 `auth_failed`、`rate_limited`、`timeout`、`incomplete`、`invalid_response`、`candidate_fetch_failed`。

### 6.3 本地精确确认

对公开候选文件内容执行完整 `Token.Key` 字节串搜索。只有本地完整比对成功才创建或更新泄露记录；只命中 16 位锚点不构成泄露。

## 7. 数据模型

新增三个独立模型文件中的表，使用 GORM 迁移并加入普通迁移与 fast migration 清单。

### 7.1 `TokenLeakScanState`

每个 token 一条当前扫描状态：

- token ID、user ID、不可逆指纹。
- token 状态快照、最后扫描开始/结束时间。
- 扫描结果：未命中、命中、不完整、失败。
- 脱敏错误码、候选数、精确命中数、搜索请求数。

不保存完整 Key、锚点、请求 URL 或响应体。

### 7.2 `TokenLeakFinding`

每个“token + 公开仓库 + 文件路径”一条泄露位置：

- 使用固定长度 `finding_key` 唯一索引，避免跨数据库长复合索引差异。
- 保存 token ID、user ID、令牌名称快照、不可逆指纹。
- 保存公开仓库 ID/全名、文件路径、Blob SHA、公开页面 URL。
- 保存首次发现、最近确认、最近通知、最近提醒时间，以及用于通知幂等恢复的重开代次。
- 状态为 `open` 或 `mitigated`，并记录处置时间与原因。

同一路径内容变化只更新 SHA 和最近确认时间；新增路径创建新记录并立即告警。搜索未命中不能自动把既有记录设为已处置，因为 GitHub 索引存在盲区。令牌禁用或删除时记录转为 `mitigated` 并停止提醒；后续重新启用且再次精确命中时重新打开并告警。

### 7.3 `TokenLeakNotification`

记录每次站内或钉钉通知尝试：

- finding ID、通知渠道、触发原因、状态、尝试次数。
- 脱敏错误码、创建与完成时间。

通知表不保存消息正文、Webhook URL、机器人 token 或令牌片段。首次/新位置事件使用幂等键避免重复；每次重新打开使用持久化重开代次生成独立幂等键，保证重复扫描不重发且后续再次重开仍会告警；单次事件最多重试 3 次，失败不终止其余令牌扫描。

## 8. 扫描编排与系统任务

新增周期全量任务 `SystemTaskTypeTokenLeakScan` 和手动任务 `SystemTaskTypeTokenLeakScanManual`，并通过独立 handler 注册到 `RegisterScheduledSystemTasks()`。两个任务类型使用同一个活动幂等键，保证全量与单 token 扫描仍然全局互斥；分开任务类型可避免手动扫描重置下一次周期全量扫描的时间基准。

### 8.1 任务载荷

- 周期全量扫描：`token_leak_scan` 任务使用空载荷或 `token_id=0`。
- 管理员全量或单条扫描：`token_leak_scan_manual` 任务只保存可选 token ID，不保存 Key 或锚点。

两个任务类型共用固定活动幂等键 `token_leak_scan`；数据库唯一约束保证任一时刻只存在一项活动泄露扫描任务。周期调度只按周期全量任务的历史计算间隔，不会被手动扫描顺延。

### 8.2 调度行为

- 只有功能开关开启且 GitHub PAT、HMAC 密钥均配置时才允许创建周期任务。
- 首次启用时没有历史任务，现有调度器会立即创建首轮任务。
- 后续按最后任务更新时间与配置间隔创建下一轮。
- handler 启动及每次外部请求前重新检查开关和 `ctx`；关闭开关后安全停止，不继续发起请求或新增扫描结果。
- 启用令牌按“从未扫描、最久未扫描”优先；其他未软删除状态使用相同规则排在后面。
- 状态进度只记录 token ID、计数、进度、脱敏错误码，不记录 Key、指纹或锚点。

任务开始时先把已禁用或已删除 token 的开放 finding 标记为已处置，确保提醒停止。任务结束结果汇总扫描数、命中数、不完整数和失败数。

## 9. 告警与处置

### 9.1 站内通知

精确命中后复用现有通知机制：

- 通过 `NotifyRootUser` 通知 root 管理员。
- 查询令牌所属用户的邮箱和通知设置后，通过 `NotifyUser` 通知该用户。

通知内容只包含 token ID/名称、用户 ID、公开仓库与文件路径、发现时间和管理处置入口。

### 9.2 钉钉机器人

- 首次精确命中或新增公开位置：立即发送 Markdown 并 `@所有人`。
- 同一开放位置未变化且令牌仍启用：距离上次成功提醒满 7 天后发送普通提醒。
- 令牌禁用或删除：停止后续提醒，但保留 finding 与通知审计。
- 钉钉失败使用脱敏错误码记录，不能把 Webhook 请求 URL或响应原文写入日志。

### 9.3 一键禁用

提供 root-only API。管理员二次确认后调用项目现有 token 状态更新与缓存同步路径，把对应 token 设为禁用，并写入 `token_leak.disable` 管理审计。操作完成后相关开放 finding 标记为已处置，但记录不删除。

## 10. API 与前端

### 10.1 Root API

- `GET /api/token-leak-scan/status`：开关、周期、凭据配置状态、队列统计、最近任务与当前任务。
- `GET /api/token-leak-scan/findings`：分页查询泄露位置，可按状态过滤。
- `POST /api/token-leak-scan/run`：触发全量或指定 `token_id` 扫描；存在活动任务时返回现有任务。
- `POST /api/token-leak-scan/findings/:id/disable-token`：确认后禁用对应 token 并审计。

所有接口只允许 root 访问；错误响应与任务响应不返回敏感值。

### 10.2 管理后台配置入口

在默认前端 `系统设置 → 安全设置 → GitHub Key 泄露扫描` 增加独立配置分区，路由为 `/system-settings/security/token-leak-scan`，只包含：

- 功能开关与 1～168 小时间隔。
- GitHub PAT、HMAC 密钥、钉钉 Webhook 的“已配置/未配置”状态。
- 最近一次 GitHub 鉴权状态。
- 固定的尽力检测声明与 GitHub 索引覆盖盲区。

该页面不承载 finding 表格和日常处置，避免把高频安全工作流埋在系统设置中。

### 10.3 Root 安全告警入口

在主侧边栏新增 root-only 导航组 `安全告警`，其中增加 `Key 泄露检测` 页面，规划路由为 `/security-alerts/token-leaks`。该页面包含：

- 最近任务、当前进度、状态队列数量和预计覆盖周期。
- 手动全量扫描与单个 token 扫描入口。
- finding 列表、公开位置链接、通知状态和筛选分页。
- 二次确认一键禁用及处置状态。
- 跳转到配置分区的设置入口。

普通用户首版不新增泄露扫描页面。用户告警只展示其自身 token 的脱敏标识与处置建议，并链接到现有 `/keys` 页面；不得把用户导向 root-only 安全告警页。

所有新增可见文案通过默认前端 i18n，补齐 en、zh、fr、ru、ja、vi。

## 11. 安全与可观测性

- 日志仅记录 task ID、token ID、计数、GitHub HTTP 状态分类和脱敏错误码。
- 不使用包含锚点的请求 URL作为错误上下文；底层网络错误先分类再记录。
- 管理 API 仅返回环境变量布尔状态。
- GitHub 与钉钉 HTTP 客户端设置独立超时、有界读取和有限重试。
- finding 公开 URL仅接受 GitHub 官方主机且由结构化响应字段构造，不直接信任任意外部 URL。
- 代码测试使用假令牌和公开非凭据字符串，不提交任何真实服务器令牌、PAT、Webhook token 或 HMAC 密钥。

## 12. 部署与回滚

### 12.1 部署门禁

实现与检查完成后，仍需用户明确授权才对目标服务器执行部署。生产开关默认关闭，先注入专用环境变量并重启服务，再用受控假令牌完成全链路验收。

### 12.2 回滚

1. 在管理后台关闭 `token_leak_scan.enabled`。
2. 确认当前扫描任务停止继续发起外部请求。
3. 移除 GitHub 与钉钉相关环境变量并重启 new-api。
4. 必要时回退应用镜像；保留新增表和审计历史，不执行破坏性删表。

关闭或回退扫描能力不得影响原有 API 转发、用户 token 鉴权和计费链路。
