# 渠道级用户每日额度限制与用量可视化

## Goal

为每个渠道增加按用户维度的每日额度上限，防止单个用户在同一渠道内消耗过多；管理员可以在渠道管理中查看当日用户额度和当前并发状态，并可把指定用户的当日已累计额度调整为目标金额。

## Background

- 现有渠道已支持 `user_concurrency_limit`，统计维度固定为 `channel_id + user_id`，同一用户的多个 Token 共享限制。
- 现有并发租约使用 Redis Sorted Set；未配置 Redis 时使用进程内存储，已配置 Redis 但不可用时失败关闭。
- 现有并发实现没有面向管理端的用户列表、当前并发数查询或清理接口。
- 主 Relay 已有统一的预扣费、结算和退款生命周期，但重试时可能切换渠道；任务、Midjourney、工具调用和违规费用还存在独立计费入口。
- 渠道管理前端已有渠道行操作菜单和独立 Dialog 模式，适合增加渠道级用户状态入口。

## Requirements

### R1. 渠道配置

- 每个渠道增加“单用户每日额度上限”配置，统计维度为 `channel_id + user_id + 自然日`。
- 同一用户的多个 Token 共享同一渠道的每日额度。
- `0`、空值和历史缺失值均表示不限制。
- 配置为 `0` 时只停止请求前的每日额度检查，所有实际结算并增加渠道 `used_quota` 的正向额度仍按用户持续记录。
- 当天中途从 `0` 启用正数限制时，立即使用该用户当天已经记录的累计额度，不重新扫描数据库或消费日志补算历史数据。
- 正向额度记录绑定最终实际记账的渠道和用户，不再由每日上限配置快照决定是否追踪；配置快照只决定对应请求是否执行上限检查。
- 配置值使用系统内部额度单位存储，前端按现有额度/货币规则输入和展示。
- 配置上限不得超过 `common.MaxQuota`，不得出现负值、溢出或显式零值丢失。
- 自然日边界沿用服务端现有每日重置语义；新的一天使用新周期，旧周期数据由过期机制自动清理，不依赖管理员手工重置。

### R2. 限额执行

- 每日额度采用软上限：请求开始时只检查已经结算的当日累计，不预占本次请求的预估额度。
- 每日额度检查必须在实际上游调用前完成；检查时累计已达到上限则返回稳定的本地 `429` 错误。
- 本地限额错误不得调用上游、不得继续预扣用户/Token 额度、不得换渠重试、不得自动禁用渠道。
- 渠道重试时，每次实际尝试都检查当前渠道的已结算累计；失败尝试不增加旧渠道的当日额度。
- 请求成功后按实际结算额度更新当日累计，普通失败且未产生结算时不增加累计。
- 每笔正向额度归属其实际记账发生的服务端自然日；跨日异步任务的初始扣费与后续正向差额可以分属不同自然日。
- 当日累计沿用渠道现有 `used_quota` 的正向使用量口径；已经记录的渠道使用量即使后续发生退款或负向调整也不自动减少，管理员可通过个人调整重设当日限制累计。
- 检查时未达到上限的请求允许继续完成，即使该请求或多个并发中的请求使实际累计超过上限；超过后到来的新请求必须被阻止。
- 软上限不承诺精确封顶，允许的超额量取决于检查时仍在途的请求数量及其最终实际额度。
- 所有会增加渠道 `used_quota` 的正向消费路径都必须同步到渠道用户当日额度；不得把预扣额度、尚未完成的请求或未结算失败计入累计。
- 正向额度记录不受当前每日上限是否为 `0` 影响；异步任务初始扣费和后续正向差额均按实际记账日记录，旧任务在新版本上线后的正向差额允许从该次结算开始记录，但不回补此前已经完成的额度。
- 已配置 Redis 但额度状态存储不可用时，正数限额的请求前检查必须失败关闭并返回稳定 `503`；限额为 `0` 时不执行检查，结算后的记录失败只写安全告警，不改写已经成功的响应。未配置 Redis 时允许与现有渠道用户并发限制一致的单实例内存模式。
- Relay 热路径不得为该功能新增数据库读写；正数限额的单次渠道尝试只增加一次轻量状态检查，所有正向结算路径执行一次实际额度更新。

### R3. 当日额度查看与个人调整

- 管理员可从指定渠道进入“用户限制状态”界面，查看该渠道当日出现过的用户额度状态。
- 即使渠道每日上限为 `0`，当日额度列表仍应展示该渠道下已经产生正向已结算额度的用户和累计金额。
- 每条额度状态至少展示用户 ID、用户名/显示名、当日已结算额度、每日上限和剩余额度。
- 列表支持刷新、空状态、加载状态和错误状态；额度按现有货币格式展示。
- 管理员可把某个用户当前自然日的已结算额度累计设置为指定目标金额；目标金额为 `0` 时等价于清空。
- 个人调整输入固定表示“调整后的已使用额度”，不是剩余额度；剩余额度始终由渠道每日上限减去已使用额度派生。
- 目标金额使用现有额度/货币输入规则，内部值必须在 `0..common.MaxQuota`，不得接受负数、NaN、无穷值或溢出值。
- 目标金额允许达到或超过渠道每日上限；达到或超过后，该用户的新请求立即被软上限检查阻止。
- 调整只影响渠道每日限额状态，不删除消费日志、不退款、不修改用户余额、Token 余额或渠道历史 `used_quota`。
- 调整不得取消该用户正在进行的请求；正在进行的请求后续完成时，其实际额度继续累加到管理员设置的目标值上。
- 调整操作必须有确认提示，明确展示用户、调整前金额和调整后金额，并使用渠道运行操作权限保护。

### R4. 当前并发可视化

- 管理员可在同一渠道级用户状态入口查看当前有并发租约的用户。
- 每条并发状态至少展示用户 ID、用户名/显示名、当前并发数和渠道配置的单用户并发上限。
- 当前并发视图在打开期间自动刷新，并提供手动刷新；过期租约不得继续显示。
- 未配置 Redis 时必须明确该数据仅代表当前实例；已配置 Redis 时展示跨实例汇总状态。
- 并发可视化不得改变现有租约获取、续租、释放、错误和取消语义。

### R5. 管理 API 与安全

- 新增渠道级只读状态 API 和单用户当日额度调整 API，沿用现有渠道权限体系。
- API 不返回 API Key、请求体、响应体、Redis 地址或其他敏感信息。
- 用户状态接口必须校验渠道存在、渠道 ID、分页/刷新参数和用户 ID。
- 每日额度超限与状态存储不可用应使用稳定错误码，并进入现有统一错误日志与管理员审计信息链路。

### R6. 前端与国际化

- 渠道编辑表单增加单用户每日额度上限配置，保留显式 `0`。
- 金额输入必须允许用户用 Backspace 暂时清空后重新输入；空值在提交时按 `0` 处理，不得在输入过程中立即回弹为 `0`。
- 编辑态金额必须使用可编辑金额精度归一化，不显示二进制浮点尾数；原生 number input 的 `step` 必须使用稳定十进制值，`600` 等正常金额不得触发浏览器步长校验错误。
- 渠道行操作菜单增加用户限制状态入口；额度和并发使用同一 Dialog 内的独立视图，避免挤入渠道主表列。
- 所有新增用户可见文案必须通过 i18n，并补齐 `en`、`zh`、`zh-TW`、`fr`、`ja`、`ru`、`vi`。
- 权限不足、状态不可用、空列表、调整确认和调整结果均需有明确界面反馈。

### R7. 薄层与兼容性

- 新增额度状态、并发查询和管理 API 逻辑优先放入独立领域文件；既有 Relay、Controller、Service 和渠道页面只保留必要的窄接入点。
- 不为本功能重构、移动、改名或格式化无关上游代码。
- 数据库相关配置必须兼容 SQLite、MySQL 和 PostgreSQL；`relaykit/` 必须保持独立可构建。
- 保持现有渠道单用户并发限制、计费、重试、任务、WebSocket 和消费日志行为兼容。

## Acceptance Criteria

- [ ] 渠道每日额度为 `0` 或历史空值时不执行请求前限额检查，但所有正向已结算额度仍按渠道和用户记录并可在管理界面查看。
- [ ] 渠道设置正数每日额度后，同一用户的多个 Token 共享当日上限，不同用户和不同渠道互不影响。
- [ ] 达到当日上限的请求在上游调用和计费前收到本地 `429`，不重试、不扣费、不禁用渠道。
- [ ] 检查时累计低于上限的并发请求允许完成并可能形成超额；累计达到或超过上限后，新请求会被阻止。
- [ ] 渠道重试按每次实际尝试的渠道检查额度，失败尝试不增加旧渠道累计。
- [ ] 流式、WebSocket、任务、Midjourney、工具调用和违规费用等正向消费路径均按实际记录额度累计；未结算失败不累计，后续退款不自动回退历史使用量。
- [ ] 新自然日开始后旧日累计不再参与限制，旧键随后自动过期清理。
- [ ] 当天从不限切换为正数限制时立即使用当天已经记录的累计；不扫描日志补算上线前或记录失败期间的历史额度，跨日正向差额计入实际记账日。
- [ ] 管理员能查看指定渠道的当日已结算额度、上限和剩余额度。
- [ ] 管理员能把单个用户的当日已结算累计调整为 `0..common.MaxQuota` 的目标金额，`0` 等价于清空。
- [ ] 个人调整不影响日志、余额、Token 和渠道历史累计；调整时存在在途请求不会取消，请求完成后实际额度继续累加。
- [ ] 管理员能查看当前有并发的用户及实时并发数，过期或已释放租约不会残留。
- [ ] Redis 多实例模式与单实例内存模式的状态范围在 API 和 UI 中表达准确。
- [ ] 所有新增 API 权限、错误码、管理员审计信息和敏感字段边界通过测试。
- [ ] 前端配置输入允许 Backspace 清空并重新输入，空值提交为 `0`，金额回填无浮点尾数，`600` 等正常值不触发原生步长校验；状态 Dialog、确认操作、自动刷新、错误/空状态、i18n、类型检查和构建通过验证。
- [ ] 原有热点文件只包含必要接入，删除新增领域模块并撤销窄接入即可回滚功能。

## 变更记录

### 变更 1：不限额时仍记录当日额度（2026-08-20）

- **原需求**：每日上限为 `0` 时完全跳过检查和记录，当天启用正数限制后只累计启用后的请求。
- **新需求**：每日上限为 `0` 时只跳过请求前检查，所有正向已结算额度继续记录；当天启用正数限制后立即使用已经记录的当日累计。
- **原因**：管理员需要在不限额渠道中持续查看用户当日使用情况，并避免启用限制时统计从零开始。
- **影响范围**：Relay 正向累计入口、异步任务差额兼容逻辑、每日额度服务测试、管理列表验收和运行风险说明。

### 变更 2：修复每日额度金额输入（2026-08-20）

- **原需求**：每日额度字段复用现有金额换算和 number input 步长。
- **新需求**：允许 Backspace 暂时清空，空值提交为 `0`；编辑态金额归一化精度，步长使用稳定十进制值。
- **原因**：当前受控输入把空字符串立即转成 `0`，原始金额换算和 `10 ** -4` 步长会暴露浮点尾数并触发浏览器原生校验。
- **影响范围**：渠道表单默认值、输入事件、公共额度步长工具及相关回归测试。

## Out of Scope

- 不实现用户全局每日额度、模型级每日额度、Token 级每日额度或渠道总每日额度。
- 不实现等待队列、按用户单独覆盖不同上限、历史多日趋势报表或额度告警通知。
- 不删除或改写历史消费日志，不把“调整当日累计”解释为退款或余额变更。
- 不在渠道主表中持续轮询所有渠道的用户并发或额度，运行状态仅在指定渠道 Dialog 打开时查询。
