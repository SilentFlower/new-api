# 非流式响应空白心跳

## Goal

为位于 Cloudflare 等带源站读取超时的反向代理之后的 New API 提供可选的非流式响应保活能力。在等待上游非流式 JSON 响应期间，New API 定期向下游写入 JSON 语法允许的前导空白并立即刷新，使代理持续收到响应数据，降低长耗时请求触发 Cloudflare 524 的概率。

该能力必须默认关闭，避免在管理员未明确接受兼容性代价时改变现有响应提交、状态码和渠道重试行为。

## Background

- Cloudflare 代理的源站读取超时默认是 120 秒；当前非流式 relay 通常会完整读取并解析上游响应后才向下游写出，等待期间前置代理收不到响应体数据。
- 当前“保持连接心跳”只在 `RelayInfo.IsStream=true` 时启用，并以 SSE 注释 `: PING\n\n` 的形式发送；该格式不能用于普通 JSON 响应。
- 标准 JSON 允许顶层值之前存在 ASCII 空格、制表符、回车和换行。非流式保活只能发送这些空白字符，不能复用 SSE 注释。
- 一旦首次空白写入并刷新，下游 HTTP 响应已开始：状态码通常固定为 200，且后续上游失败不能再按原行为安全地改写状态码；现有渠道重试策略也必须显式处理这一状态。
- 当前非流式响应会在解析成功后复制允许透传的上游响应头；首次空白心跳早于上游响应头到达时，这些后到的响应头无法再写入已经提交的下游响应。
- `RELAY_IDLE_CONN_TIMEOUT`、TCP keepalive 和 `Connection: keep-alive` 只涉及连接复用或传输层存活，不能代替应用层响应数据。

## Requirements

### R1. 配置与默认值

- 新增独立的“非流式响应保活”开关，默认关闭，老配置缺少该字段时必须保持关闭。
- 配置入口与现有“保持连接心跳”和“Ping 间隔（秒）”放在同一设置区域。
- 流式 SSE 心跳与非流式空白心跳共用现有 `ping_interval_seconds` 作为发送间隔，但两个开关相互独立；任一开关启用时，间隔输入均可编辑。
- 面向用户的开关名称、说明和风险提示必须覆盖 `web/default` 支持的全部语言。

### R2. 下游空白心跳

- 仅在开关启用、请求为非流式且目标响应协议确定允许 JSON 前导空白时启动。
- 每个间隔向下游写入 JSON 合法的 ASCII 空白字符并立即 Flush；不得写入 `: PING`、NUL、BOM 或其他会破坏 JSON 的字节。
- 上游在首次间隔到达前完成时，不得写入额外空白，不得改变现有响应状态、响应体或重试行为。
- 请求取消、客户端断开、上游请求结束或 handler 退出时必须及时停止心跳，不得泄漏 goroutine 或继续写入已复用的 Gin context。
- 并发写入必须受控，不能让心跳与最终 JSON、错误响应或其他 handler 写入交错。

### R3. 协议与端点边界

- 不得向音频、文件下载、图片二进制、WebSocket、SSE 或其他非 JSON 响应写入空白。
- 不得把“上游响应 Content-Type”作为等待首个上游响应头之前的唯一判断条件，因为保活需要覆盖等待上游响应头的阶段。
- 具体支持的 relay mode/endpoint 必须采用明确允许列表，并通过测试锁定，避免未来新增二进制端点时被自动纳入。
- 首期允许列表覆盖所有能够在发起上游请求前确定最终响应为 JSON 的 relay 协议，至少包括 Chat Completions、Completions、Responses、Responses Compact、Claude Messages、Gemini、Embeddings、Moderations、Rerank、Image Generations 和 Image Edits。
- 图片生成与图片编辑是本功能的核心场景，不能因其位于独立 `ImageHelper` 路径而遗漏；非流式图片 URL 和 `b64_json` 响应都属于 JSON 响应。

### R4. 状态码、错误与重试

- UI 必须明确提示：首次保活数据写出后，HTTP 状态码已提交；如果所有渠道最终都失败，下游实际 HTTP 状态只能是 200，并通过标准 JSON 错误体表达失败。
- 后端必须能判断本请求是否已写出非流式心跳，不得继续假设响应尚未提交。
- 首次心跳写出后仍沿用现有渠道重试规则。只要尚未写出最终业务响应，前导空白不得被视为禁止重试的业务数据；后续渠道成功时必须正常返回成功 JSON。
- 所有重试均失败时，返回与对应 relay format 一致的标准 JSON 错误体，并在错误体可兼容承载的字段及服务端日志中保留原始错误状态/错误代码，实际 HTTP 状态允许为 200。
- 如果上游失败发生在首次心跳之前，必须保持现有错误 HTTP 状态码和重试行为，不得提前降级为 200。
- 最终成功响应在标准 JSON 解析后的对象必须与关闭该功能时一致；允许原始响应字节多出前导空白。

### R5. 兼容性与可观测性

- 不得设置与实际分块响应冲突的固定 `Content-Length`。
- 必须验证当前 gzip/代理中间件不会吞掉 Flush；若无法保证，应在设计中明确禁用缓冲或压缩的处理方式。
- 日志应能区分是否启用了非流式保活以及是否实际写出过心跳，但不得按每次心跳产生高频普通日志。
- 如果首次心跳早于上游响应头到达，接受不再向下游透传后到的 provider 响应头；该限制只影响实际写出过心跳的请求，首次间隔前完成的请求必须保持现有响应头行为。
- New API 自身请求 ID 必须保持可用；上游请求 ID 即使无法下发，也必须继续写入请求上下文和服务端日志用于排查。

## Acceptance Criteria

- [ ] AC1：新安装和缺少新字段的历史配置中，非流式响应保活均为关闭状态，现有请求行为不变。
- [ ] AC2：启用后，一个允许列表内、上游等待时间超过心跳间隔的非流式 JSON 请求，在最终 JSON 前收到至少一个已 Flush 的合法空白心跳；心跳不会产生 EOF、HTTP/1.1 结束块或 HTTP/2/3 `END_STREAM`，下游读取必须继续等待最终 JSON。
- [ ] AC3：同类请求在上游于首次间隔前完成时，原始响应体不增加空白，状态码和渠道重试行为与现状一致。
- [ ] AC4：带一个或多个前导心跳的成功响应可被标准 JSON 解析器解析，解析结果与未启用时完全一致。
- [ ] AC5：音频、二进制文件、WebSocket、SSE 和未列入允许列表的端点绝不启动非流式空白心跳。
- [ ] AC6：客户端取消和上游结束后，心跳 goroutine 在受控时间内退出，测试不存在退出后的继续写入。
- [ ] AC7：首次心跳写出后，渠道失败仍按现有规则重试；后续渠道成功时返回可正常解析的成功 JSON，所有渠道失败时返回 HTTP 200 + 对应协议的标准 JSON 错误体，并保留原始错误信息。
- [ ] AC8：设置页在现有保持连接心跳配置旁展示新开关、说明及风险提示，保存和重新加载后状态一致，所有支持语言均有翻译。
- [ ] AC9：实际写出心跳后，不设置错误的固定 `Content-Length`，不尝试下发后到的 provider 响应头；New API 请求 ID 和服务端记录的上游请求 ID 仍可用于排查。
- [ ] AC10：后端相关单元测试、`go test ./...`、前端 i18n 检查、类型检查、lint 和生产构建通过。

## Out of Scope

- 不调整 Cloudflare 账户侧 Proxy Read Timeout，也不承诺消除所有网络层 524。
- 不改变上游服务自身的 keepalive 配置。
- 不把非流式响应改造成 SSE，不改变成功 JSON 的字段结构。
- 不为二进制响应设计额外的封装协议。
