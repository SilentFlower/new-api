# 修复 Responses WebSocket 并发长期占用

## 目标

让渠道单用户并发反映正在执行的 Responses WebSocket 请求数，保留空闲连接及多轮续接能力。

## 背景与证据

- 2026-11-16 09:11—09:14 UTC，渠道 #52 上限为 5；刘英轲（用户 26）的同一组 5 个 Redis 租约持续续期。其中一个连接最后完成于 09:04:42 UTC，09:13:02 UTC 时距最后完成已 500 秒。
- `controller/responses_websocket.go:430` 将租约保存至连接退出；`:435` 执行最终释放；`:597` 在回合终止后仅清空 currentTurn。
- `service/channel_user_concurrency.go:217` 每 30 秒续租，TTL 为 120 秒；持续续租使空闲连接一直计入并发。
- 09:14:23 UTC 按用户授权精确清理 5 个租约后读数为 0；09:14:58 UTC 确认旧租约全部退出，客户端重建 4 个连接。
- 官方协议与 Codex 源码确认连接复用属于正常行为，连接内缓存用于增量续接，见 `research/websocket-concurrency.md`。
- 既有 `.trellis/spec/backend/channel-user-concurrency.md:145` 与多轮测试按连接持有租约；本任务按用户于本轮确认的请求级口径修正这一契约。

## 已确认决定

- 并发按正在执行的 response.create 请求计算；空闲连接继续复用。
- 每轮开始独立获取名额，完成、失败、取消终态或断开后释放；下一轮重新检查。
- 本地并发拒绝沿用现有 WebSocket 错误封套、稳定错误码和连接结束行为。
- 实现先交付代码、测试和检查结果；生产部署作为独立运维步骤处理。

## 需求

- R1：空闲连接占用零个请求并发名额；同一连接多轮普通及 Compact 请求均独立持有名额。
- R2：每轮在预扣与实际上游发送前检查同渠道同用户的有效并发上限；满额与存储不可用保持稳定本地 429/503、跳过重试与渠道禁用处理。
- R3：父子共享限制和个人覆盖每轮重新解析；当前回合的限制归属固定，后续回合读取最新有效关系。
- R4：终止、客户端断开、上游断开、准备失败、发送失败、续租丢失与既有重试路径均正确释放；既有成功结算和失败退款保持幂等。
- R5：保留同连接的增量续接、普通/Compact 交替、模型与分组资格检查以及原始帧透传行为。

## 验收标准

- [x] AC1 / R1：生成期间计数为 1，终止后连接仍可复用且计数为 0，下一轮重新计为 1；普通与 Compact 均覆盖。
- [x] AC2 / R2：多个空闲连接共存时仍可进入请求；实际活动请求达到上限时，额外请求在预扣及上游发送前被拒绝。
- [x] AC3 / R3：每轮使用生效的父桶或个人覆盖；轮间父关联变化后下一轮占用新归属。
- [x] AC4 / R4：成功、失败、取消终态、准备/发送失败、断开和重试均释放名额，续租丢失保持现有 503 及请求终止语义。
- [x] AC5 / R4、R5：多轮普通/Compact 账务、增量续接、取消转发及资格变化重连回归通过，定向竞态检查通过。

## 范围边界

- 聚焦 Responses WebSocket 并发租约的请求生命周期与对应规范。
- Realtime 继续按连接持有租约；其他 HTTP 和任务协议保持既有规则。
- 本轮不引入空闲断连配置、连接数量限制或 stream_id 多路并发支持。
- 本地 Flower 同步及已有工作区变更独立保留；本任务的提交范围单独确认。
