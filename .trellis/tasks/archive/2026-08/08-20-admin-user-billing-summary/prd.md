# 管理员用户账务批量摘要接口

## Goal

为管理端提供一次请求批量读取多个用户钱包、订阅和 NewAPI 远端账号事实的能力，消除调用方逐用户请求造成的 N+1 延迟，并为钱包余额与订阅周期剩余额度提供统一、可跨批次合并的全局排序契约，同时保持现有账务与权限边界。

## Background

- AI Fund 用户管理列表当前会逐个读取 NewAPI 用户详情，默认 20 条、并发 5，最多形成 4 批串行等待。
- NewAPI 已有管理员用户列表和单用户订阅接口，但没有面向跨系统管理列表的批量账务摘要接口。
- 钱包 `quota` 是当前可用余额，不能减去累计 `used_quota`；订阅额度由 `amount_total`、`amount_used`、状态、有效期和重置时间独立决定。
- `amount_total = 0` 表示无限订阅，不得解释为零额度。
- AI Fund 的门户状态/角色与 NewAPI 状态/角色属于不同事实源；列表需要同时展示两者，但刷新列表不得自动同步、启停或提权。
- 本期同时纳入订阅周期剩余额度全局排序，并与现有钱包余额排序使用统一排序字段。

## Requirements

- 新增管理员鉴权的只读批量查询能力，一次请求只查询调用方明确提供的用户 ID，不接受无条件全量扫描。
- 输入用户 ID 必须为正整数，严格去重，单批最多 500 个；空列表、非法 ID、超限请求必须在数据库查询前拒绝。
- 请求使用统一的 `sort_by` 字段选择排序目标，允许值为 `user_id`、`wallet_quota`、`subscription_remaining`；`sort_order` 只允许 `asc` 或 `desc`。
- 响应中的每个用户结果必须返回统一 `sort_key`，其类型区分 `finite`、`infinite`、`unknown`，使调用方合并多个批次后仍可复现服务端排序语义。
- `wallet_quota` 的排序值为原始可用 `quota`；`subscription_remaining` 的有限排序值为所有有效有限订阅当前周期剩余额度之和，任一有效无限订阅存在时标记为 `infinite`。
- 没有有效订阅是已知的零剩余额度，不能标记为未知；用户不存在或单用户订阅数据无法可靠计算时标记为 `unknown`，且无论升序或降序都置底。
- 有限值按 `sort_order` 排序；订阅无限值在降序时排在有限值之前、升序时排在有限值之后；同类同值统一以用户 ID 倒序作为稳定并列顺序。
- 响应必须覆盖钱包余额、钱包累计已用、用户分组、有效订阅摘要，以及 NewAPI 原生 `remote_status` 和 `remote_role`。
- `remote_status` 原样返回 `User.Status` 整数值，当前有效值为启用 `1`、禁用 `2`；`remote_role` 原样返回 `User.Role` 整数值，沿用 NewAPI 现有角色常量。
- `remote_status` 和 `remote_role` 仅用于展示远端事实与差异提示；批量读取不得根据门户值自动修改 NewAPI，也不得根据 NewAPI 值自动修改门户权限。
- 每个有效订阅摘要必须包含套餐 ID、套餐名称、有限/无限标记、当前周期总额、已用、剩余、有效期和下次重置时间。
- 已取消、已过期或已超过有效期的订阅不得计入有效订阅汇总。
- 已到重置时间但后台维护任务尚未落库时，摘要必须按实际消费时的懒重置语义计算；读取接口不得为了展示主动写回订阅。
- 多个有效订阅必须稳定汇总；任一无限订阅存在时明确标识无限，不能用特殊大整数冒充。
- 有限订阅聚合必须防止 `int64` 加法溢出；发现异常数据时将该用户标记为读取错误，不得返回负数或错误排序值。
- 返回结果必须按用户 ID 可关联，并明确区分 `ok`、`not_found` 和 `error`；`ok` 且有效订阅列表为空表示确实没有订阅。
- 全局数据库查询失败时整个请求返回失败；单个用户的缺失套餐、非法订阅数据或聚合失败不得影响其他合法用户结果。
- 接口不得返回密码、Access Token、API Key、支付载荷、用户邮箱或其他与本摘要无关的敏感字段。
- 查询实现必须使用 Model 层批量读取用户、有效订阅和相关套餐，不产生逐用户数据库查询，不新增数据库迁移。
- 遵守薄层开发原则：Router 只注册路由和鉴权；Controller 只绑定请求、调用 Service 和转换响应；Service 只编排校验、批量读取、摘要聚合和排序；Model 只提供批量持久化读取及与现有消费路径共享的订阅周期投影规则。
- 订阅周期重置规则只能有一个权威实现，摘要读取与实际预消费必须复用同一投影逻辑，禁止复制近似算法。
- 保持现有单用户钱包、订阅和用户列表接口兼容，不改变既有前端行为。
- 提供覆盖批量参数、排序契约、远端状态/角色、钱包语义、有限/无限/多个订阅、周期重置边界、无订阅、无效用户、局部异常、敏感字段和权限控制的回归测试。

## Acceptance Criteria

- [ ] 管理员可在一次 HTTP 请求中查询最多 500 个用户的钱包、订阅及 NewAPI 远端状态/角色；未授权和普通用户不能调用。
- [ ] 同一批中的用户、有效订阅和套餐通过固定次数的批量数据库查询处理，不产生逐用户 Controller、HTTP 或数据库自调用。
- [ ] `sort_by` 统一支持用户 ID、钱包余额和订阅周期剩余额度，多个批次可依靠响应 `sort_key` 合并后得到稳定全局顺序。
- [ ] 钱包余额为原始可用 `quota`，累计已用单独返回。
- [ ] 每个命中用户返回原生 `remote_status` 与 `remote_role`，AI Fund 无需逐用户请求即可展示门户值与 NewAPI 值及其差异。
- [ ] 批量读取远端状态/角色不会触发自动启停、角色同步或权限提升。
- [ ] 有限订阅正确返回当前周期剩余量；多个有限订阅安全求和；无限订阅明确返回无限标记。
- [ ] 无订阅按已知零值参与订阅剩余额度排序；无限、未知、并列和升降序均符合稳定顺序。
- [ ] 到期、取消及无效订阅不计入汇总；到期重置边界与实际计费的懒重置语义一致，且摘要查询不写数据库。
- [ ] 单个用户不存在或数据异常时有明确结果，其他合法用户仍可返回；全局查询错误不伪装成部分成功。
- [ ] 响应不泄露密码、Access Token、API Key、支付载荷或邮箱。
- [ ] SQLite、MySQL、PostgreSQL 使用相同 GORM 查询语义，无数据库专用 SQL，且有自动化测试保护关键行为。
- [ ] Controller、Service、Model 保持薄层边界，没有重复的参数校验、订阅周期计算或排序规则。
- [ ] 现有用户、订阅及计费测试保持通过。

## Out Of Scope

- 修改钱包扣费、订阅扣费优先级或钱包兜底规则。
- 修改订阅计划、购买、重置、失效和删除等写操作。
- 在本批量读取接口中执行 NewAPI 用户启停、提权、降权或与门户角色自动同步。
- 修改现有用户列表接口以直接联表返回订阅摘要。
- 支持除用户 ID、钱包余额、订阅周期剩余额度之外的任意排序表达式。
- 为 AI Fund 实现页面文案、筛选控件、分页、差异提示或列表展示；调用方改造由 AI Fund 任务负责。
- 新增数据库表、字段、索引或迁移。
