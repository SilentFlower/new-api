# 优化视觉辅助模型选择与消息审计

## 目标

降低渠道视觉辅助配置的操作成本，把视觉辅助调用作为独立消息审计记录保存和展示，并避免 `combined` 模式因无限合并图片产生超大请求或破坏跨对话缓存复用。

## 背景与已确认事实

- 当前渠道编辑页把辅助渠道配置为数字输入框，把辅助模型配置为普通文本输入框，管理员必须手工查找并填写渠道 ID 与模型名，见 `web/src/features/channels/components/drawers/sections/build-channel-settings.tsx:409`。
- 项目已有“启用渠道 + 渠道配置模型”的精简查询能力，查询只读取 `id`、`name`、`models`，不返回渠道密钥，见 `model/message_audit_review_options.go:5`。
- 消息审计目前只在主请求进入 `controller.Relay` 并完成 DTO 校验后捕获一次原始入站请求，见 `controller/relay.go:133`。
- 视觉辅助请求不会再次进入 `controller.Relay`；它在 `relay.callVisionAssistModel` 中完成协议转换、计费并直接调用渠道适配器，见 `relay/vision_assist.go:91`。因此当前视觉辅助内部请求不会触发消息审计，用户观察属实。
- 消息审计已经能够规范化 OpenAI Chat、OpenAI Responses、Claude Messages 和 Gemini Native DTO；视觉辅助的四种端点模式均可复用现有正文脱敏、媒体摘要和加密存储能力。
- 视觉辅助命中缓存时不会发起辅助模型调用，也不会重复扣费；缓存命中不应伪造辅助请求审计记录。
- 视觉辅助的每个缺失识图单元会独立执行，并可按配置重试；每次进入辅助渠道调用的尝试都具有独立请求 ID。

## 需求

### R1：辅助渠道选择

- 把“辅助渠道 ID”数字输入改为可搜索的渠道选择器。
- 选项只展示当前启用且管理员有权读取的渠道，至少显示渠道名称和渠道 ID，避免同名渠道无法区分。
- 选项接口只返回配置所需的精简字段，不返回密钥、代理鉴权或其他敏感配置。
- 编辑历史配置时，即使已保存渠道已停用、删除或不在当前选项中，也必须保留并明确展示当前值，不能静默清空。
- 切换辅助渠道后清空旧辅助模型，避免保存“新渠道 + 旧模型”的无效组合。

### R2：辅助模型选择

- 辅助模型选项随所选渠道联动，来源为该渠道已配置的模型列表。
- 模型控件支持搜索和选择，同时保留自定义模型名输入能力，以兼容渠道尚未登记但上游实际支持的模型。
- 未选择渠道时禁用模型选择；渠道没有配置模型时展示明确空状态，但仍允许输入自定义模型。
- 编辑历史配置时，已保存模型即使不在当前渠道模型列表中也必须继续显示，并提示该模型不在当前选项中。
- 加载失败、无可用渠道、历史值失效和模型列表为空必须有可理解的界面状态。

### R3：视觉辅助独立消息审计

- 视觉辅助请求作为独立消息审计记录展示，不合并到主请求正文。
- 每条视觉辅助审计记录必须标识为“视觉辅助”，并保存关联主请求 ID。
- 视觉辅助记录详情可跳转到主请求；主请求详情可查看并打开其关联的全部视觉辅助记录。
- 每次缓存未命中且成功构造有效辅助 DTO 的调用尝试生成一条独立记录；重试产生新的独立记录，缓存命中不生成记录。
- 审计正文必须对应协议转换和模型映射后准备交给辅助渠道的 DTO，而不是主请求或未转换的中间请求。
- 审计支持 OpenAI Chat、OpenAI Responses、Claude Messages 和 Gemini Native 四种视觉辅助端点模式。
- 捕获内容继续使用现有消息审计的加密、媒体摘要、大小限制、队列和保留策略；不得保存原始图片二进制、完整 data URL 或远程图片正文。
- 辅助 DTO 捕获后发生的 token 估算、定价、并发、预扣费、上游调用或响应处理失败必须正确 finalize，不能长期停留在 `pending`。
- 辅助请求必须使用独立审计会话，不参与普通用户会话的前缀/压缩归并，也不得进入主请求会话的 AI 重审材料。
- 消息审计未启用、密钥未配置或队列拒绝写入时，视觉辅助请求仍按现有逻辑执行，审计失败不能影响转发或计费。

### R4：兼容性与边界

- 历史消息审计记录缺少新增类型和关联字段时，按普通客户端请求展示。
- 视觉辅助与主请求的关联不建立数据库外键；主记录被保留策略删除后，辅助记录允许保留不可跳转的历史关联 ID。
- 不改变视觉辅助触发、缓存、重试、失败策略、并发控制、计费和主请求改写语义。
- 不改变未开启视觉辅助的渠道、纯文本请求和透传请求。
- 前端新增或修改的用户可见文案必须同步七种语言。
- Base UI 受控选择器必须始终渲染当前值对应选项，并保持键盘、焦点和 Drawer 内交互可用。
- build 分支定制逻辑优先放入独立文件，原有上游文件只保留最薄接入点。

### R5：Combined 模式自动分批

- `combined` 模式必须增加“单批最大图片数”渠道级配置，配置字段为 `combined_max_images`，默认值为 `5`，合法范围为 `1-64`。
- 历史渠道配置缺少该字段、字段为 `0` 或字段越界时，后端执行和前端编辑态都必须回退到默认值 `5`，不能继续无限合并。
- 当同一用户消息中的图片数量超过上限时，必须按原始图片顺序自动切割为多个识图单元；例如上限为 `5` 时，`12` 张图片拆为 `5 + 5 + 2`。
- 自动分批不得跨用户消息合并图片；`separate` 模式仍保持每张图片一个识图单元。
- 分批后的识别结果必须保留全局图片顺序和编号，最终仍由目标模型结合全部批次的文字结果完成综合回答。
- 现有 `max_concurrency`、缓存、重试、计费和失败策略按分割后的识图单元继续生效。
- 自动分批必须是确定性的：相同渠道、模型、提示词、用户问题、图片内容与顺序，在不同请求 ID、审计会话、消息位置和并发调度下必须产生相同批次及相同缓存键。
- 已成功识别并写入缓存的批次，在缓存 TTL 内被新的对话请求以相同输入再次提交时必须直接复用，不得因自动分批新增重复的辅助模型调用或重复计费。
- 缓存键不得包含请求 ID、审计会话 ID、消息索引、批次序号或并发 worker 信息；必须继续基于实际影响识别结果的渠道、模型、提示词、用户问题及有序图片内容生成。
- 调整 `combined_max_images` 导致批次图片组合发生变化时，不得错误复用旧组合的联合识别结果；若实际批次图片组合未变化，则允许继续命中原缓存。
- 后端必须使用固定的 `8 MiB` 单批内联图片请求体安全上限；达到图片数上限前如果已超过该上限，也应提前切割。单张图片自身超过安全上限时允许独立成批，并交由现有失败策略处理。
- 普通日志必须记录实际批次数、各批图片数、是否发生自动切割以及生效的 `combined_max_images`，便于定位大批量视觉辅助请求。
- 渠道编辑页仅在 `combined` 模式下展示“单批最大图片数”数字配置，修改保存后对后续请求动态生效，无需重启服务。

## 非目标

- 不自动探测辅助渠道上游尚未登记的全部模型。
- 不修改目标模型匹配、视觉提示词、`separate` 模式或其他视觉辅助参数的业务语义。
- 不提供请求体字节上限的前端配置；本轮只开放图片数量上限，字节上限作为后端安全常量。
- 不重构原始图片转发策略，不新增持久图片路径、对象存储句柄或图片编辑 Agent 协议；自动分批仅保持现有 `strip_image` 语义。
- 不把缓存命中伪装成实际辅助模型调用。
- 不保存视觉辅助模型的原始响应正文；消息审计仍只保存请求正文和请求结束元数据。
- 不把视觉辅助记录并入主请求的推断会话或 AI 重审材料。
- 不让管理员触发的消息审计 AI 重审请求进入消息审计。
- 不新增按视觉辅助类型筛选消息审计的列表过滤器。

## 关键决定

- 采用“独立记录 + 关联主请求”，不把视觉辅助正文嵌入主请求详情。
- 一个实际辅助调用尝试对应一条记录；视觉辅助内部重试会产生多条关联记录。
- 关联采用普通索引字段，不建立外键，避免异步写入、保留清理和三数据库兼容性受到耦合。
- 模型选择保留自定义值能力，不能因模型不在渠道当前配置列表中阻止历史配置或特殊上游模型。
- `combined` 不再表示同一消息内图片无限合并，而是按渠道配置和后端安全上限进行有界分批；默认每批 `5` 张。
- 为了让渠道设置 JSON 能被现有解析链路识别，本次允许在独立可构建的 `relaykit/dto.ChannelVisionAssistSettings` 中增加可选字段，并补充 `GOWORK=off` 构建验证。

## 验收标准

- [ ] 管理员可以按渠道名称或 ID 搜索并选择辅助渠道，不再手填渠道 ID。
- [ ] 选择渠道后可搜索其配置模型，并可输入自定义模型名。
- [ ] 切换渠道会清空旧模型；历史失效渠道或模型仍可见且有明确提示。
- [ ] 选项加载、空数据和失败状态不会导致表单值丢失或 Drawer 运行时错误。
- [ ] 每个非缓存命中的视觉辅助调用尝试生成独立消息审计记录，并明确标识为视觉辅助。
- [ ] 视觉辅助记录可跳转到主请求，主请求详情可打开全部关联辅助记录。
- [ ] 审计正文与最终辅助协议 DTO 一致，且不保存原始图片正文。
- [ ] OpenAI Chat、OpenAI Responses、Claude Messages 和 Gemini Native 视觉辅助请求均有回归覆盖。
- [ ] 辅助审计记录不会与普通用户会话归并，也不会进入主请求会话 AI 重审材料。
- [ ] 辅助 DTO 捕获后的成功和失败路径均正确 finalize；审计不可用时不影响视觉辅助调用。
- [ ] 缓存命中不新增视觉辅助请求审计记录。
- [ ] 历史审计记录和历史视觉辅助配置保持可读、可编辑。
- [ ] `combined` 模式的单批最大图片数可按渠道配置，默认 `5`，合法范围 `1-64`，旧配置自动使用默认值。
- [ ] 同一消息的超量图片按原始顺序稳定拆批，不跨消息合并；`separate` 模式行为不变。
- [ ] 图片数或后端请求体安全上限触发切割时，日志可看到实际批次数、批次大小、切割状态和生效上限。
- [ ] 分批后缓存、重试、并发、计费、失败策略及最终图片编号顺序保持正确。
- [ ] 自动分批不改变 `strip_image` 行为：关闭移除时原始图片内容与顺序保持不变，开启移除时仍只向目标模型注入识图文字。
- [ ] 两个独立请求上下文在缓存 TTL 内提交相同问题和相同有序图片时，第二次请求全部命中分批缓存，辅助 caller 调用次数为 `0`；请求 ID、消息位置和并发顺序变化不影响命中。
- [ ] 分批上限变化造成图片组合变化时不会误命中旧联合结果，未改变实际图片组合的批次仍可安全复用。
- [ ] 前端定向测试、类型检查、lint、格式检查和生产构建通过；后端定向测试、`go test ./...` 与 `go vet ./...` 通过。

## 变更记录

### 变更 1：Combined 模式有界分批（2026-08-16）

- **原需求**：`combined` 将同一用户消息内的全部图片放入一个视觉辅助请求，不提供单批上限。
- **新需求**：增加渠道级 `combined_max_images` 配置，默认 `5`、范围 `1-64`；超量图片自动按顺序分批，并保留固定请求体安全上限。
- **原因**：线上请求曾将 `39` 张图片合并为约 `12.7 MB` 的 Gemini 请求，上游两次返回 HTTP 200 但无可解析文本，最终触发 `empty_response`。
- **影响范围**：`relaykit` 渠道设置 DTO、视觉辅助单元构造与日志、渠道表单解析/保存/UI、七语言文案及前后端回归测试。

## 已记录风险

- 当前 `strip_image=true` 会从目标请求移除原始图片，可能使需要圈选、裁剪或编辑图片的 Agent 无法取得原始像素。
- `strip_image=false` 会同时向目标模型发送识图文字和原始图片，可能产生重复视觉处理；目标模型不支持视觉时还可能返回请求格式错误。
- 当前图片来源只在请求期内表示为 URL 或 Base64，内部磁盘缓存路径是临时资源，不是可供 Agent 跨请求使用的稳定路径。
- 上述问题需要单独设计模型能力判断、图片资产权限、存储期限和 Agent 工具契约，本轮不自动选择保留策略，也不新增持久化图片句柄。
