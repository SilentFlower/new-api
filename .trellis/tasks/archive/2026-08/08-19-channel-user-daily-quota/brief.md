# Brief — 渠道级用户每日额度限制与用量可视化

## Goal

- 为渠道增加按用户维度的每日额度软上限，持续记录渠道下用户的当日正向已结算额度，并让管理员查看当日额度和当前并发状态、调整指定用户的当日已用额度。

## Scope

- 在渠道配置中增加“单用户每日额度上限”，按 `channel_id + user_id + 服务端自然日` 统计，同一用户的多个 Token 共享额度。
- 在每次实际选渠尝试的上游调用和预扣费之前检查已经结算的当日累计；达到上限时返回本地 `429`，不调用上游、不扣费、不换渠重试、不自动禁用渠道。
- 使用 Redis Hash 保存多实例共享的当日状态；未配置 Redis 时使用单实例内存状态；新自然日自动切换状态周期并通过 TTL 清理旧数据。
- 将每日累计与现有渠道 `used_quota` 的正向记账点对齐，覆盖普通 Relay、流式、WebSocket、任务、Midjourney、工具调用、视觉辅助和违规费用等路径；即使每日上限为 `0` 也持续记录。
- 新增渠道管理 API，用于分页查看当日用户额度、把单个用户的当日已用额度设置为目标值，以及查看当前有并发租约的用户。
- 扩展现有渠道用户并发租约服务，维护可枚举的渠道用户索引并提供只读实时统计，不改变原有限制、续租、释放和取消语义。
- 在渠道编辑表单增加每日额度配置，修复金额回填浮点尾数、原生步长校验和 Backspace 无法清空的问题；在渠道行操作中增加“用户限制状态” Dialog，并以“每日额度”和“当前并发”两个 Tab 展示状态。
- 补齐七种前端语言、权限和错误反馈、后端行为测试、前端交互测试及三数据库兼容验证。

## Non-Goals

- 不实现用户全局、模型级、Token 级或渠道总量级的每日额度。
- 不实现等待队列、严格预占封顶、按用户覆盖不同上限、历史多日趋势或额度告警通知。
- 不删除或改写消费日志，不把当日累计调整解释为退款，也不修改用户余额、Token 余额或渠道历史 `used_quota`。
- 不在渠道主表持续轮询所有渠道的运行状态；只在指定渠道的状态 Dialog 打开时查询。
- 不重构无关的 Relay、计费、任务、渠道表单或并发租约框架。

## Key Decisions

- 每日额度采用软上限：请求开始时只检查已结算累计，不预占本次请求估算额度；检查时未达上限的在途请求允许完成，因此可以小幅超额，达到或超过后才阻止后续请求。
- 渠道额度配置为 `0`、空值或历史缺失值时表示不限，只跳过请求前检查；所有正向已结算额度仍持续记录，当天启用正数限制后立即使用已有累计。
- 每次实际选渠的额度配置进入 `ChannelMeta` 快照并只决定是否检查；正向记账始终绑定最终实际渠道和用户。异步任务初始扣费及后续正向差额按实际记账日记录，旧任务从新版本上线后的正向差额开始记录，不扫描日志补算此前数据。
- 每笔正向额度计入实际记账发生的服务端自然日；跨日任务的初始扣费与后续正向差额可以分属不同日期。退款或负向调整不回退已记录的历史正向使用量。
- 个人操作固定表示“调整后的已使用额度”，允许设置 `0..common.MaxQuota`；`0` 等价于清空。调整不取消在途请求，在途请求完成后的实际额度继续累加。
- Redis 已配置但状态不可用时，正数限额的请求前检查失败关闭并返回稳定 `503`；限额为 `0` 时不检查，结算记录失败仅告警。未配置 Redis 时允许内存模式，并在 API 和 UI 明确仅代表当前实例。
- 每日额度状态使用渠道级 Redis Hash，不在 Relay 热路径读写数据库，也不使用 `KEYS` 或 `SCAN`；并发用户索引在现有 Lua 获取/释放调用中维护，不额外增加租约获取的 Redis 往返。
- 渠道表单回填使用 `quotaUnitsToEditableAmount`，提交使用 `parseQuotaFromDollars`；空字符串作为临时编辑状态并在提交时归一化为 `0`，number input 步长使用稳定十进制值。
- 管理列表使用 `ChannelRead` 权限，个人额度调整使用 `ChannelOperate` 权限；接口不返回密钥、请求内容、余额或 Redis 内部信息。

## Key Context

- 渠道配置与迁移入口位于 `model/channel.go`；选渠上下文位于 `middleware/distributor.go` 和 `constant/context_key.go`；最终渠道快照位于 `relay/common/relay_info.go`。
- 现有并发契约和实现位于 `.trellis/spec/backend/channel-user-concurrency.md` 与 `service/channel_user_concurrency.go`，必须保持现有租约 key、TTL、心跳和错误行为兼容。
- 每日额度领域逻辑计划集中在 `service/channel_user_daily_quota.go`；管理接口集中在新的渠道用户限制 Controller，旧热点文件只增加必要的检查、配置传递或正向累计调用。
- 正向累计必须逐项对齐当前 `model.UpdateChannelUsedQuota` 调用点；`ChannelUserDailyQuotaTracked` 不再门控异步任务差额记录，旧 JSON 仍需兼容读取。
- 管理路由接入 `router/channel-router.go`；前端入口位于现有 Channels Provider、Dialog 注册、行操作菜单、渠道表单、API 和类型模块。
- 可编辑额度换算和步长工具位于 `web/src/lib/format.ts`；渠道表单默认值与输入交互位于 `web/src/features/channels/lib/channel-form.ts` 和 `components/drawers/channel-mutate-drawer.tsx`。
- 所有数据库变化必须兼容 SQLite、MySQL 和 PostgreSQL；涉及 `relaykit/` 错误码后必须使用 `GOWORK=off` 验证其独立构建。
- 所有新增前端文案必须通过 `i18next`，并补齐 `en`、`zh`、`zh-TW`、`fr`、`ja`、`ru`、`vi`。

## Risks / Deferred

- 软上限的最大超额量由检查时仍在途的请求数量和实际费用决定；这是已接受的性能与精度取舍，现有用户并发限制可约束峰值。
- 多实例必须使用一致的服务端时区，否则自然日边界和 `reset_at` 会不一致。
- 上游已经成功后若每日额度累计写入失败，只能记录带 request ID 的安全告警，不能改写已返回的成功响应；Redis 未恢复期间正数限额请求会在前置检查返回 `503`，限额为 `0` 的请求继续执行但故障期间记录无法补算。
- Redis 并发用户索引可能因进程异常残留，管理查询必须清理过期租约和空用户，索引本身也要设置 TTL。
- 内存模式只适用于单实例准确统计；多实例部署必须使用 Redis 才能得到全局额度和并发状态。

## Acceptance

- 限额为 `0` 或历史空值时不执行请求前状态读取，但正向已结算额度仍写入每日状态并可在管理界面查看。
- 正数限额下，同一用户的多个 Token 共享渠道当日额度，不同用户和渠道互不影响。
- 达到上限的新请求在上游调用和计费前收到稳定 `429`，且不重试、不扣费、不禁用渠道；低于上限时允许请求完成并产生可接受的软超额。
- 重试按每次实际候选渠道检查，失败尝试不累计旧渠道；正向额度只在现有渠道使用量记账成功路径累计，失败、预扣和负向退款不累计。
- 新自然日不再读取前一日累计；当天从 `0` 启用正数限制后立即使用当天已有累计，不扫描日志回补未记录历史，跨日异步任务正向差额计入实际记账日。
- 管理员能查看用户 ID、用户名/显示名、当日已用额度、上限和剩余额度，并把指定用户的当日已用额度设置为 `0..common.MaxQuota` 的目标值。
- 个人调整不修改日志、余额、Token、渠道历史额度或当前并发；目标达到或超过上限后新请求立即被阻止，在途请求完成后继续累加。
- 管理员能查看当前有有效租约的用户、实时并发数和渠道并发上限；过期或释放的租约不会继续显示，Dialog 关闭后停止轮询。
- Redis 多实例模式和内存单实例模式表达准确；Redis 已配置但不可用时启用限额的请求返回稳定 `503`。
- 新增 API 的参数、分页、权限、稳定错误码、审计信息和敏感字段边界通过测试。
- 前端每日额度输入允许 Backspace 清空并重新输入，空值提交为 `0`，回填不显示浮点尾数，`600` 等正常值不触发原生步长校验；状态 Dialog、确认操作、刷新/轮询、空/错/加载状态、七语言、类型检查、Lint 和构建通过验证。
- 后端定向测试、Race 测试、全仓测试、`go vet`、三数据库兼容检查及 `relaykit` 独立构建通过。
