# GitHub 公共仓库 Key 泄露扫描

## Goal

在用户指定的 `www.havefun.eu.cc` 服务器上，为 new-api 建立 GitHub 公共内容用户令牌泄露检测能力，及时识别本实例签发的用户 API Key 是否出现在公开仓库中，并提供可追溯且不泄露完整令牌的告警结果。

## Background

- 本任务只扫描 `model.Token.Key` 保存的 new-api 用户调用令牌，不扫描 `model.Channel.Key` 上游渠道凭据。
- 用户令牌由 `common.GenerateKey()` 生成，为 48 位大小写字母和数字随机串；对外规范形式是 `sk-<tokens.key>`。
- 认证逻辑会移除 `sk-` 前缀，并允许 `sk-<tokens.key>-<client-suffix>` 形式，因此泄露识别不能依赖完整字符串在分隔符后结束。
- GitHub 官方 Partner Secret Scanning 主要面向凭据发行方；本功能需要评估普通仓库/API 能力可达到的覆盖范围及其盲区。
- GitHub Code Search 支持全站公开代码的精确字符串检索，但自动化调用受鉴权、独立搜索限流和搜索索引覆盖范围约束。
- 本地 PoC 使用仓库内公开的假测试令牌 `owner1234token5678` 验证：只向 GitHub 发送 16 位搜索锚点即可发现候选 Blob，下载候选后可在本地完成完整令牌精确比对，并能拒绝仅末位不同的误报。
- 匿名调用 GitHub Code Search REST API 返回 HTTP 401；完成用户确认的 GitHub CLI 设备授权后，本地 PoC 使用 16 位假锚点搜索到 83 个公开候选，`incomplete_results=false`，并准确定位 `QuantumNous/new-api` 的 `controller/token_test.go`。
- 安全真阳性实验选取 GitHub 公共默认分支中真实存在、但不是凭据的 48 位字母数字字符串 `TestAdminResetPlanSubscriptionsResetsAllActiveUs`；随机偏移 `29` 得到 16 位锚点 `nsResetsAllActiv` 后，从公开文件 `model/subscription_reset_test.go:140` 命中锚点，完整 48 位精确比对成功，并拒绝仅末位不同的变体。该实验验证两阶段算法，不涉及发现、展示或验证第三方真实凭据。
- 用户同意由本地环境发起 GitHub 授权；进一步核对官方文档后确认，GitHub CLI 设备登录的最低权限固定包含 `repo`、`read:org`、`gist` 且不能移除，明显高于公开代码检索所需权限，因此实际授权前必须再次确认风险或改用最小权限凭据。
- GitHub 官方 REST 文档确认 `Search code` 支持 fine-grained personal access token，且该接口不要求额外仓库权限；正式运行应使用独立、短有效期、无额外仓库权限的 fine-grained PAT，而不是 GitHub CLI 生成的宽权限 OAuth 登录令牌。
- 用户确认了解上述权限会覆盖其私有仓库，并接受本地 PoC 临时使用该 GitHub CLI 登录态；PoC 期间只允许读取公开代码搜索结果，不得读取、修改或枚举私有仓库内容。
- 用户授权从目标服务器只读选取一个真实的启用用户令牌进行受控 PoC；完整令牌不得离开目标服务器，只允许随机连续 16 位锚点发送到 GitHub，且不得改变该令牌状态或调用它验证有效性。
- 目标服务器已成功通过 SSH 完成只读环境检查：Debian 主机使用 Docker 部署，new-api 容器镜像为 `ghcr.io/silentflower/new-api:build-bak-latest` 且健康，数据层为 MySQL 8.2 与 Redis；new-api 数据和日志使用宿主机绑定挂载。
- 真实令牌 PoC 只读选取令牌 ID `13`（用户 ID `15`、启用状态、48 位、最近访问优先），在服务器内存中随机截取 16 位锚点进行 GitHub 公开代码搜索；结果为 `search_total=0`、`incomplete_results=false`、`exact_matches=0`，未发现公开候选。该结果只表示本次锚点和当前 GitHub 索引未命中，不构成绝对无泄露保证。
- PoC 完成后已退出本地 GitHub CLI 登录，并关闭交互 SSH 与临时 SSH 复用通道；未改变目标令牌、数据库或容器状态。
- 当前本地环境已无 GitHub CLI 登录态，因此没有可直接迁移到目标服务器的现存授权令牌；即使重新进行 CLI 设备授权，其固定宽权限也不符合正式部署的最小权限要求。
- 用户进一步授权在功能开发前执行一次性全量只读扫描，覆盖目标服务器全部未软删除用户令牌；已确认当前范围为 92 个启用令牌和 1 个禁用令牌，共 93 个。
- 首次全量扫描在完成 25 个令牌后主动终止：查询未限定公开可见性，而临时 GitHub CLI 凭据具有私有仓库访问权限，理论上可能把账号可访问的私有仓库结果误判为公开泄露。前 25 个查询均无候选，但该批次不作为最终全量公开扫描结果。
- 公开范围校验发现 REST Code Search 不接受 `is:public` 查询写法：已知存在于公开仓库的测试令牌在加入该限定后返回 0。最终方案使用不带 `repo`、`user`、`org` 限定的全网查询，并在响应端只处理 `repository.private=false`；正式运行还必须使用不具备私有仓库读取能力的专用凭据。
- 修正后的全量公开扫描从头覆盖 93 个未软删除令牌，结果为：成功查询 93、查询失败 0、无效长度 0、不完整查询 0、截断查询 0、公开候选 0、私仓忽略 0、候选下载失败 0、精确命中 0。该结论仅代表每个令牌本次随机 16 位锚点在当前 GitHub 索引中未命中。
- 连续 16 位锚点不会对“完整令牌在已索引文件中原样连续出现”的场景增加漏报：完整字符串包含其任一连续子串。漏报主要来自 GitHub 只搜索仓库默认分支、索引延迟或缺失、历史/已删除内容不可见，以及令牌被拆行、字符串拼接、转义或编码后不再包含所选连续子串。
- 目标服务器登录凭据仅用于本次受控检查和后续确认后的部署，不得写入仓库、任务文档、脚本、命令历史或应用日志。

## Requirements

- 扫描数据源必须来自目标 new-api 实例的 `tokens` 表，不允许依赖手工导出明文清单。
- 扫描对象是确认状态范围内的用户令牌；应识别 `sk-<tokens.key>`、裸 `<tokens.key>` 以及后接客户端后缀的形式。
- 扫描所有未软删除的用户令牌：启用状态进入高优先级队列，禁用、耗尽和过期状态进入低优先级队列；软删除记录不扫描。
- 检索、比对、日志、持久化和告警全过程不得输出完整 Key；结果仅记录渠道或令牌标识、不可逆指纹、泄露位置、首次及最近发现时间和状态。
- 禁止把完整用户令牌发送给 GitHub 或其他第三方搜索接口。
- 每个令牌只向 GitHub Code Search 发送一个连续 16 位搜索锚点；正式功能使用扫描专用密钥对完整令牌做 HMAC，并由摘要稳定派生窗口偏移，使同一令牌每次只暴露同一个片段，避免重复扫描逐渐向 GitHub 暴露更多字符。获取候选公开文件后，在目标服务器内存中使用完整令牌进行精确比对。
- 搜索 URL、HTTP 错误、调试日志、任务状态和指标不得记录 16 位搜索锚点；完整令牌与搜索锚点均不得持久化到扫描结果表。
- 扫描任务必须有速率限制、超时、重试和可取消机制，不能影响 new-api 的转发请求与数据库稳定性。
- 调度采用持续低速队列，GitHub Code Search 默认上限为每分钟 8 次搜索 HTTP 请求；分页请求同样计入预算。启用令牌优先，其他未软删除状态低优先级补扫，并提供管理员手动扫描单个令牌的入口。
- 泄露扫描作为可配置的周期性系统任务运行，接入项目现有 `system_task` 调度、互斥和状态管理机制；多节点部署只由主节点调度执行，不新增宿主机 cron 或独立常驻 ticker。默认每 24 小时完成一轮，管理员可配置为 1～168 小时；首次启用后立即创建首轮任务，后续按上一轮结束时间计算间隔。
- 一次性全量扫描同样遵守每分钟不超过 8 个 Code Search 请求；逐条只输出令牌 ID、用户 ID、状态和扫描结论，完整令牌及锚点只存在于内存，扫描结束后立即退出 GitHub 登录并关闭 SSH 通道。
- 泄露判定范围必须是 GitHub 全站公开仓库，而不是仅扫描授权账号名下仓库；查询不得带 `repo`、`user` 或 `org` 范围限定，响应端必须拒绝 `repository.private=true` 的候选，私有仓库命中不得计为泄露结果。若响应被截断或存在无法判定可见性的候选，该令牌必须标记为扫描不完整。
- 部署前只允许对目标服务器执行只读环境检查；实施和线上变更必须在规划评审通过后进行。
- 远端启用定时扫描前，必须在目标服务器完成受控假令牌全链路验收，并验证 GitHub 连通性、鉴权、限流处理、数据库兼容性、任务互斥、日志脱敏、功能开关和回滚路径；任一关键检查失败时保持扫描任务关闭。
- 目标服务器不得复用开发者个人 GitHub CLI 登录态；正式扫描必须使用独立、可撤销、最小权限且可轮换的 GitHub 凭据，并通过服务器密钥配置注入。
- GitHub 专用凭据只允许通过目标服务器环境变量注入，不在数据库或管理后台保存、回显明文；管理后台只配置扫描开关和周期，并展示凭据是否已配置及最近一次鉴权状态。轮换凭据通过更新服务器环境变量并重启服务完成。
- 正式凭据确定使用独立的 fine-grained PAT，不复用个人 GitHub CLI OAuth 登录；令牌不授予额外仓库权限，设置明确有效期并按到期时间轮换。
- 精确确认泄露后只发送告警，不得自动禁用用户令牌。
- 精确确认泄露后同时通知系统管理员和令牌所属用户；两类通知均不得包含完整令牌或 16 位搜索锚点，只展示令牌标识、公开位置、发现时间和处置入口。
- 泄漏告警必须支持钉钉外部通知，不能依赖用户主动访问 new-api 页面。首版确定通过自定义机器人 Webhook 把精确命中推送到固定安全告警群；Webhook 凭据只通过服务器环境变量注入，消息仅包含脱敏令牌标识、所属用户、公开位置、发现时间和处置链接。首版不新增钉钉用户身份字段、不建立账号映射，也不发送机器人单聊。
- 钉钉告警节奏确定为：首次精确命中或出现新的公开泄漏位置时立即推送并 `@所有人`；同一泄漏位置未变化且令牌仍启用时每 7 天发送一次普通提醒；令牌禁用或删除后停止提醒，但保留泄漏记录和通知审计。
- 管理员可从泄露结果执行一键禁用；操作前必须二次确认，并记录不含令牌明文的管理审计日志。
- 管理端 UI 拆分为两个入口：`系统设置 → 安全设置 → GitHub Key 泄露扫描` 只负责功能开关、扫描周期和外部凭据配置状态；主侧边栏新增 `安全告警 → Key 泄露检测`，承载任务进度、手动扫描、泄露列表、通知状态和一键禁用等日常处置功能。
- 普通用户首版不新增泄露扫描页面；收到站内或外部通知后，使用现有 API Keys 页面禁用或重新创建自己的令牌。用户通知中的处置入口不得指向仅 root 可访问的管理页面。
- 产品文案必须明确该能力是尽力检测，不能宣称具备 GitHub Secret Scanning Partner 的全量覆盖或零漏报保证。
- 未命中结果必须明确列出覆盖边界：只覆盖 GitHub 当前可搜索索引中的公开仓库默认分支，不能覆盖未索引文件、非默认分支、历史提交、已删除内容或经过拆分与编码的令牌。

## Acceptance Criteria

- [ ] 能从 `tokens` 表枚举确认状态范围内的全部用户令牌，并为每条令牌生成稳定的不可逆指纹。
- [ ] 调度顺序优先覆盖启用令牌，并能展示各状态最近扫描时间、待扫描数量和预计完整覆盖周期。
- [ ] 周期扫描接入现有 `system_task` 调度器，默认每 24 小时执行一轮并允许配置 1～168 小时；首次启用立即执行，支持开关、任务互斥、主节点单实例执行、失败重试和管理员手动触发，关闭后不得继续创建或执行扫描任务。
- [ ] 扫描过程中应用日志、数据库结果和告警内容均不包含完整凭据。
- [ ] GitHub 请求不包含完整令牌，且日志与持久化数据不包含完整令牌或 16 位搜索锚点。
- [x] 对测试用公开仓库中的已知测试凭据能够返回准确的仓库、文件或提交位置。
- [x] 对已知公开候选文件能够在本地完成 16 位锚点初筛、完整测试令牌精确确认，并拒绝相近字符串误报。
- [ ] 对未发现结果明确展示扫描时间、覆盖范围和已知盲区，不把“未命中”等同于“绝对未泄露”。
- [ ] 重复扫描同一泄露位置可幂等更新，不产生无限重复告警。
- [ ] 精确命中后同时向管理员和令牌所属用户发送脱敏告警，重复扫描不得对同一未变化泄露位置无限重复发送通知。
- [ ] 配置钉钉告警后，精确命中能向指定安全群发送 Markdown 告警；发送失败会记录脱敏错误并进入有限重试，不影响扫描任务继续处理其他令牌。
- [ ] 首次命中和新增泄漏位置的钉钉告警会 `@所有人`；未处置且仍启用的同一泄漏每 7 天至多提醒一次，令牌禁用或删除后不再提醒。
- [ ] 发现泄露不会自动改变令牌状态；管理员确认后可一键禁用对应令牌，并可审计操作人、时间和令牌 ID。
- [ ] GitHub 限流、鉴权失败、网络故障或目标内容删除时，任务能记录明确状态并安全退出。
- [ ] 目标服务器部署不在文件、环境输出、进程参数或 Shell 历史中留下登录密码和被扫描 Key。
- [ ] 提供最小回滚步骤，停用扫描功能不影响 new-api 主服务。
- [x] SSH 环境检查完成前不得制定依赖特定容器、数据库或目录结构的部署步骤。
- [ ] 目标服务器使用受控假令牌完成“数据库读取 → GitHub 搜索 → 候选下载 → 本地精确比对 → 结果持久化 → 告警”的全链路验收，且验收后清理测试数据。
- [ ] 目标服务器主动验证 GitHub 鉴权失败、限流和网络超时场景；失败时不阻塞 new-api 主服务、不产生错误禁用、不泄露令牌。
- [ ] 关闭功能开关并执行回滚步骤后，扫描调度、后台请求和新增写入全部停止，new-api 原有 API 转发保持正常。
- [ ] 正式 GitHub 凭据不具备仓库写入、组织管理或 Gist 写入能力，撤销或轮换后扫描任务能给出明确鉴权错误且不影响主服务。
- [ ] 使用无额外仓库权限的专用 fine-grained PAT 能完成 GitHub 公共代码搜索与公开候选下载，并证明无法读取私有仓库内容。
- [ ] 管理后台和配置 API 不返回 GitHub 凭据明文；凭据只从服务器环境变量读取，日志、任务状态和错误信息不得泄露请求头或令牌内容。
- [ ] 系统设置中的泄露扫描分区只包含配置与凭据状态；root 主侧边栏存在独立的 `安全告警 → Key 泄露检测` 处置页，配置与日常告警处置不会混在同一设置页面。
- [ ] 普通用户无需访问 root 处置页即可根据通知定位自己的 token，并能从现有 API Keys 页面完成禁用或重新创建。
- [x] 真实令牌 PoC 只输出令牌 ID、用户 ID、扫描状态和公开候选位置；完整令牌与 16 位锚点不出现在本地终端、任务文档、日志或持久化结果中。
- [x] 一次性全量扫描覆盖全部 93 个未软删除令牌，记录成功、未命中、不完整、查询失败、候选下载失败和精确命中数量，并对任何精确命中仅报告令牌 ID 与公开位置。

## Out of Scope

- 冒充凭据持有者申请 GitHub Secret Scanning Partner 资格。
- 扫描 `channels.key` 中的上游供应商凭据。
- 自动调用或试用发现的凭据来验证其有效性。
- 未经确认自动禁用、删除或轮换生产凭据。
- 钉钉应用机器人单聊、new-api 用户与钉钉 `userId` / `openDingTalkId` 的自动映射。
