# 合并 v1.0.0-rc.24 到 build-bak

## 目标

将官方 `v1.0.0-rc.24` 标签对应提交 `5c3abffe8572aa8a49f15c3916707d2019d66af4` 完整合并到当前 `build-bak` 分支，在吸收上游架构、认证、RelayKit、计费与前端目录调整的同时，保留 `build-bak` 已有定制功能和对 `/root/project/ai-fund` 的兼容性。

本任务处理到本地合并、冲突消解、功能核对和质量验证完成；最终提交与推送按 Trellis 提交门禁另行确认。

## 已确认基线

- 当前目标分支：`build-bak`，规划时提交为 `63c77d5ad`。
- 合并来源：官方标签 `v1.0.0-rc.24`，提交为 `5c3abffe8572aa8a49f15c3916707d2019d66af4`。
- 共同祖先：`7c28993f6`。
- 相对共同祖先：`build-bak` 独有 250 个提交，`rc.24` 独有 77 个提交。
- 临时工作树试合并发现 96 个未解决路径：47 个双方修改、28 个本地修改但上游删除、18 个上游新增但本地已有、3 个双方新增。
- 冲突主要分布：`web/root` 40 个、`web/classic` 24 个、`relay` 12 个、`i18n` 4 个、`controller` 4 个、`relaykit` 3 个、`web/default` 2 个，其余位于 `service`、`model`、`middleware` 等目录。
- 历史合并任务的既有原则是：跟随上游结构和迁移方式，在新结构上重建并保留 `build-bak` 定制行为，避免简单整侧取舍。

## 需求

### R1. 精确控制合并范围

- 只合并 `v1.0.0-rc.24` 的精确标签提交，不带入该标签之后的 `main` 更新。
- 合并前记录并校验 `build-bak` 起点，建立可恢复的本地备份引用。
- 使用真实 Git merge 保留双方历史，不通过 squash 或复制文件伪造合并结果。

### R2. 按语义解决冲突

- 每个冲突都必须结合共同祖先、`build-bak` 版本和 `rc.24` 版本判断，禁止批量采用 `ours` 或 `theirs`。
- 上游结构变化优先落地；`build-bak` 的业务能力迁移到上游新结构，而不是恢复已被上游淘汰的旧架构。
- 遵循上游友好定制规范：定制逻辑尽量留在独立文件，上游文件仅保留必要接入点，避免借合并进行无关重构。

### R3. 吸收 rc.24 核心变化

- 前端目录调整：将 Default 前端从 `web/default/` 迁移到上游扁平化后的 `web/` 结构。
- 认证与会话：接入无状态 JWT、会话控制及相关中间件/路由/model 变化。
- RelayKit：接入上游抽取后的公共 relay 能力和 provider 适配结构。
- 计费：接入分层计费、用户组切换及相关 DTO、服务和日志变化。
- 通道与协议：接入 rc.24 新增或调整的 Sub2API、NewAPI、腾讯等通道能力。
- HTTP：接入上游 HTTP/2、请求体重放与重试相关改动，并与本地重试逻辑合并。
- 数据库迁移、依赖、生成文件、路由、i18n 和构建配置保持与新结构一致。

### R4. 保留 build-bak 定制能力

以下能力必须逐项建立“原入口 -> 冲突处理 -> 新入口 -> 验证证据”的核对记录：

- 消息审计与 AI 审核。
- GitHub 密钥泄漏扫描。
- 通道级用户并发限制。
- Responses Compact V1/V2/WebSocket 透传。
- Alpha Search。
- 视觉辅助能力。
- Claude WebSearch 模拟。
- 按映射后的上游模型计费。
- 公共 API Key 日志。
- 控制台 Excel 导出与筛选。
- Token 迁移。
- User-Agent 日志。
- 非流式 JSON keepalive。

### R5. 认证兼容性与 ai-fund 契约

- 保留 Personal Access Token 校验回退链路，不能因 rc.24 的 JWT/会话改造而只允许新会话令牌。
- 保留 API Key 的只读日志查询能力及现有鉴权语义。
- `/root/project/ai-fund` 使用的 `Authorization: Bearer <NEWAPI_ACCESS_TOKEN>` 和 API Key 调用继续可用。
- `New-Api-User` 在新认证链路中即使不再必需，也不得导致旧客户端请求失败。
- 默认不修改 `ai-fund`；只有发现无法在 `new-api` 侧兼容的明确契约问题时，才另行说明并请求范围确认。

### R6. 计费与 relay 安全不回退

- 合并后的预扣费、结算、退款、倍率、模型映射和日志必须同时覆盖双方逻辑，不能因冲突消解丢失任一侧的计费分支。
- 保持配额计算的饱和保护、异常审计、显式零值透传和跨数据库兼容要求。
- HTTP 请求重试必须确保请求体可重放，且不能造成重复扣费、重复写日志或不可控重试。

### R7. 前端功能迁移

- 跟随 rc.24 正式移除 Classic 前端，不继续维护 `web/classic/`。
- `build-bak` 在 Default 前端上的页面、筛选、导出、日志和管理能力必须迁移到新的 `web/` 目录。
- 所有用户可见文本继续覆盖 en、zh、fr、ru、ja、vi 六种语言。
- 合并后只保留一套有效的前端依赖、构建脚本和生成产物入口，避免新旧目录同时参与构建。

### R8. 验证与可恢复性

- 合并完成后不存在 Git 冲突状态、冲突标记、意外删除或未解释的大范围整侧覆盖。
- 后端至少完成格式化、静态检查、受影响包测试及全量可行测试；前端完成依赖一致性、i18n 检查和生产构建。
- 对认证、PAT、API Key 日志、relay 重试、计费、前端关键功能执行针对性回归。
- 形成合并报告，列明冲突分类、主要取舍、保留功能、验证结果和剩余风险。
