# 多个渠道共享用户并发与额度限制

## 目标

通过子渠道关联父渠道，让多个渠道共用父渠道的限制配置和计数，避免切换渠道绕过上限，并保持 ai-fund 无需修改源码。

## 用户原始需求

> 我想实现一个功能，现在的渠道里面设置的并发和金额之类，只有一个渠道。能不能同时关联多个渠道，让他们作为一个整体去呢？比如我限制并发是4，假如第5个请求进来能拦住，然后也不要因为这个错误，进行重试请求关联的渠道。

## 背景与证据

- 现有并发以渠道和用户为维度，同一用户跨令牌共享，不同渠道互不影响。依据：`.trellis/spec/backend/channel-user-concurrency.md:10`。
- 渠道并发配置位于 `model/channel.go:54`；金额配置已迁移到预算 v2，包含个人/池子、日/周/整段、模型和时段。依据：`dto/channel_period_policy.go:28`、`.trellis/spec/backend/channel-period-budget-fallback.md:7`。
- 本地并发和额度错误已跳过普通重试，但 HTTP 文本另有显式额度降级，需要共同验证。依据：`controller/channel_user_concurrency.go:123`、`controller/channel_user_quota_limits.go:23`、`controller/relay.go:235`、`controller/channel_limit_fallback.go:61`。
- ai-fund 每个号池映射单个渠道，管理读写均使用该渠道 ID。调查仓库为用户指定的 `/root/project/ai-fund`，依据保存在 `research/ai-fund-impact.md`。

## 需求

- R1：父渠道 A 与关联子渠道 B、C 按用户共用一份并发计数和上限；同一用户跨令牌共享，不同用户独立。
- R2：上限为 4 时，同一用户在 A/B/C 合计已有 4 个请求执行，第 5 个请求在预扣费和上游调用前返回本地 429；释放名额后可以进入，不排队。
- R3：同一共享限制触发后，不因该错误普通重试父渠道或其他子渠道，不自动禁用渠道。已有显式金额降级必须检查目标的有效限制，不能绕过同一共享预算。
- R4：A 是唯一限制配置来源，B 使用 A 的并发、预算及个人提额。B 原配置保留，解除关联后恢复，不叠加两套规则。
- R5：A 保留当前周期已有累计；B 只把关联后开始的新请求产生的新增正向消费计入 A，不搬迁 B 关联前的历史用量。关联、解除和变更关系不清零 A 的累计。
- R6：继承为单向关系。修改 A 的限制自动对 B 生效；B 的继承项只读，页面及直接 API 调用均不能通过 B 反向修改 A。修改共享配置时进入 A 的管理入口。
- R7：B 的上游地址、密钥、类型、模型及物理渠道身份独立；请求实际到达 B 的上游，消费账单和日志仍记录 B。
- R8：ai-fund 继续映射和管理 A，原有状态、并发配置、预算、用量和个人提额接口保持兼容；不修改 ai-fund 源码。若原来映射 B，只需通过现有设置改为 A。
- R9：new-api 提供父渠道选择、继承来源查看及解除关联。仅支持一级父子关系，拒绝自身关联、循环、多级关系和删除仍被关联的父渠道。
- R10：在途请求及异步任务使用开始时确定的限制归属，后续关联变更不移动已持有名额或把旧任务结算改记到新父渠道。新关联的统一上限在切换前在途请求结束后验收。
- R11：金额沿用已有软上限语义，只检查已结算用量，不预占本次费用；金额零值、不限、免费请求、退款及预算种类沿用现有行为。

## 已确认决定

- D1：用户答复「这个按推荐来」，确认按用户在关联渠道内合计限制并发，不采用所有用户合计的并发上限。
- D2：用户答复「这个按你建议来」，确认共用一套并发、预算和个人提额，原渠道配置保留供解除关联后恢复。
- D3：用户提出「B 渠道关联 A 渠道」「关联父渠道」，以现有 A 作为限制权威，满足 ai-fund 不改源码的目标。
- D4：用户答复「只读是吧，我觉得可以」，确认 B 的继承限制只读、单向继承，不反向写 A。
- D5：用户答复「这个按你建议就行」，确认 A 保留已有累计，B 仅从关联后的新增消费开始计入 A，B 历史用量不回填。

## 范围与约束

- 本轮只修改 new-api。ai-fund 仅做只读合同验证，源码和 D1 映射数据不由本任务自动改写。
- 前端入口沿用渠道用户限制弹窗，在其中查看或设置父渠道，继承预算、用量及个人覆盖时明确展示只读状态；并发输入入口同样体现继承。
- 多实例继续要求 Redis；仅内存时只保证当前进程。已有请求结束、缓存传播等切换边界须在 UI 说明，不能宣称绑定时会自动迁移所有在途名额。
- 共享金额是限制状态，不是财务合并；不回写历史消费日志、钱包、令牌余额或物理渠道历史 used_quota。
- 不实现独立限制组、多级继承、请求排队、严格金额预占、历史回填或 ai-fund 成员管理。

## 验收标准

- [x] A1（R1、R2）：同用户在 A、B 各有 2 个请求时，第 5 个请求返回 429；释放 1 个后可进入。
- [x] A2（R3）：共享超限时，即使配置普通重试次数，也不请求 A 或其他子渠道，不预扣、不重复日志、不自动禁用。
- [x] A3（R5、R11）：关联渠道消费合并进入 A 的适用预算；到限后 A/B 均被拦截，软上限及退款行为保持原合同。
- [x] A4（R1）：同一用户换令牌不能绕过上限；另一用户仍有自己的并发名额。
- [x] A5（R4、R6）：修改 A 的并发、预算、个人提额后 B 使用新值；通过 B 写继承项被明确拒绝，A/B 原配置均不被误写。
- [x] A6（R4、R5）：解除关联后 B 恢复原独立配置，A 的配置和已用累计保持不变。
- [x] A7（R7）：实际调用 B 的模拟上游且唯一消费日志记为 B，限制计数归 A。
- [x] A8（R8）：ai-fund 映射 A 时，现有读取、并发保存、预算、用量与个人提额合同可用，无需改源码。
- [x] A9（R5）：关联前 A 已用 3、B 已用 2，关联后 A 仍为 3；B 新请求消费 1 后 A 为 4，不搬迁 B 的旧 2。
- [x] A10（R9）：自身关联、循环、多级关系、过期版本覆盖关系和删除仍有子渠道的父渠道均被拒绝，精简候选列表不含密钥。
- [x] A11（R10）：HTTP、WebSocket、任务、Midjourney 和视觉辅助沿用一致的限制归属；重试、取消、释放和任务后续结算不串桶、不重复累计。
- [x] A12（R6、R8）：界面可查看继承来源和父配置，继承项只读、解除后恢复编辑；既有未关联渠道及缺少新快照的历史任务保持兼容。
