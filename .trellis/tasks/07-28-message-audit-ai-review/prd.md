# 消息审计 AI 自动审核与总结

## Goal

在现有 Root-only 消息审计中，为管理员提供基于已保存审计正文的 AI 内容审核与摘要能力，降低人工逐条阅读成本，同时保持消息正文的加密、权限、保留期和普通日志隔离边界。

## Background

- 现有消息审计只保存经过过滤的客户端入站可见内容；请求结束时仅补充模型、状态、错误码、完成原因、HTTP 状态和耗时，不保存当前请求的模型响应正文（`service/message_audit.go:300`、`.trellis/spec/backend/logging-guidelines.md:228`）。
- 单条详情只有 Root 管理接口会按需解密正文，且每次查看都会记录不含正文的管理审计日志（`controller/message_audit.go:57`、`service/message_audit.go:331`）。
- 审计请求已按 `audit_session_id` 推断会话，前端详情页支持在同一推断会话内切换请求（`model/message_audit.go:23`、`web/default/src/features/message-audits/components/message-audit-detail.tsx:195`）。
- 当前数据模型、服务 DTO 和前端类型中没有 AI 审核结果、摘要、风险等级、审核模型版本或审核任务状态字段（`model/message_audit.go:23`、`service/message_audit.go:101`、`web/default/src/features/message-audits/types.ts:21`）。
- 消息正文不得进入普通应用日志、消费日志、ClickHouse 日志或管理操作审计；AI 审核链路也必须遵守同一隔离规则。
- 消息审计 capture 先保存请求阶段模型，finalize 再异步把非空最终消费模型更新到同一记录（`model/message_audit.go:446`）；列表直接展示缓存行的 `model_name` 并用同一行的 `request_id` 打开详情（`web/default/src/features/message-audits/index.tsx:248`、`web/default/src/features/message-audits/index.tsx:723`），详情则通过独立查询读取当前数据库值（`web/default/src/features/message-audits/api.ts:83`）。
- 消息审计列表没有自动刷新，而全局 React Query 配置关闭窗口聚焦刷新并设置 10 秒 `staleTime`（`web/default/src/features/message-audits/index.tsx:173`、`web/default/src/main.tsx:54`）。因此 finalize 发生在列表查询之后时，列表可能继续显示采集阶段旧模型，详情显示 finalize 后正确模型；这是当前模型显示不一致的高概率根因。
- 当前 capture 位于请求 DTO 校验和 `GenRelayInfo` 成功之后、渠道选择和上游调用之前（`controller/relay.go:116`、`controller/relay.go:133`、`controller/relay.go:138`）。因此认证/格式/正文大小等前置失败不会保存正文；通过校验后发生的无可用渠道、额度、并发或上游失败会保留并在 finalize 标记为 `failed`（`controller/relay.go:151`）。
- 后端已有按模型统计或估算文本 Token 的 `service.CountTextToken`，OpenAI 模型使用 tokenizer，其他模型使用估算（`service/token_counter.go:401`）；但当前后端渠道和模型元数据没有可统一依赖的上下文窗口字段，因此不能假设系统能自动知道任意审核模型的真实上下文上限。
- 单次规范化正文累计超过 1 MiB 时，service 返回 `entries=nil` 并把 `audit_status` 标记为 `metadata_only`（`service/message_audit.go:606`、`service/message_audit.go:286`）。这类记录只保存请求元数据，不创建 `message_audit_blobs` 或 `message_audit_items`；列表上的“内容大小”表示降级前已统计的规范化正文大小，不是实际已存密文大小。
- metadata-only 记录当前没有消息块、序列指纹或锚点，`assignMessageAuditSession` 只能为每次请求新建会话；因此截图中多条相同的 654 消息、278 工具、约 1 MiB 失败请求会显示为多个“1 个请求”，并非正文被重复存储。
- metadata-only 记录没有可解密正文，因此无论采用分块还是 Tool，AI 都无法审核这类历史记录；若要覆盖截图中的超大请求，必须调整当前 1 MiB 全量丢弃正文的策略。
- 未超限的正常记录按同一用户、schema version 和内容 HMAC 复用加密消息块，每个请求只新增有序引用（`model/message_audit.go:200`）；媒体二进制在规范化阶段已剥离，不会作为文件重复保存。
- 消息审计元数据已保存 `error_code`、`http_status` 和 `finish_reason`，但当前列表和详情均未展示这些字段（`service/message_audit.go:309`、`web/default/src/features/message-audits/types.ts:38`）。直接保存或展示任意上游错误原文可能包含被回显的敏感内容，不符合审计隔离边界。
- 当前压缩会话推断通过同用户、同协议的消息锚点有序子序列识别 `compressed`，并统计同一会话内的压缩次数（`model/message_audit.go:332`、`model/message_audit.go:487`）。连续多次压缩只要仍有足够且唯一的历史锚点即可留在同一会话；若后续压缩丢失过多锚点或产生歧义，系统会保守地新建会话。
- 生产 MySQL 观测显示，消息审计启用约 3 小时 39 分钟后相关表空间已约 505 MiB；`message_audit_items` 约 161 万行，而 blob 约 4.1 万行，说明跨请求去重有效，但当前每条消息仍逐条尝试插入 blob、冲突后查询 ID、再逐条写 item，形成显著语句和索引访问放大。
- 压缩会话命中比例很低，但当前候选查询先从历史请求、item 与 blob 联表筛选 HMAC；性能统计中 item 的 `audit_request_id` 索引读取远高于 `blob_id` 索引读取，表明该路径会扫描大量不匹配历史消息项。
- 状态接口每次读取都会对审计请求、item、blob 做全表统计和 payload 汇总；当前单次 item COUNT 已达到约 260 ms、payload SUM 约 160 ms，并被前端固定轮询重复触发。
- 生产 MySQL 的 128 MiB InnoDB buffer pool 明显小于约 3.17 GiB 主库，应用默认最大连接数 1000 也高于 MySQL `max_connections=151`；数据库配置需要与应用连接池共同收敛，但代码仍必须先消除不必要的查询和写入放大。

## Requirements

- AI 审核只能由 Root 管理员使用，列表接口不得因此返回原始正文、密文或 nonce。
- AI 输入必须来自消息审计 service 解密后的受控数据，不得从普通日志或未验证的原始请求旁路读取。
- 第一版审核现有消息审计已经保存的完整客户端入站会话上下文，包括客户端提交的 system、user、assistant 和 tool 角色；不新增当前请求模型响应正文采集，模型回复只有在客户端后续作为历史重新提交时才会进入审核材料。
- 审核由 Root 管理员人工触发，目标粒度固定为一个 `audit_session_id` 推断会话；不按单次请求分别生成审核结果。
- 系统设置新增全站固定的“消息审计 AI 渠道”和“消息审计 AI 模型”；设置页按“渠道下拉选择 → 模型下拉选择”联动配置，模型选项只展示所选渠道可用模型。
- 每次审核直接使用系统设置中的固定渠道和模型，不在审核弹窗中重复选择或临时覆盖；未配置、渠道已停用或模型不再可用时不得猜测或自动切换，必须提示 Root 前往系统设置修正。
- 每个推断会话只维护一份当前审核结果；管理员可对该会话手动重审。
- 风险等级与审核任务/新鲜度状态必须独立保存和展示。“内容已变化，待重审”不能覆盖上一次成功审核的风险等级；例如列表应同时显示“高风险”和“待重审”。
- 重审排队、运行或失败期间继续保留上一次成功结果及其审核时间、依据和覆盖范围；只有新的重审成功后才原子替换当前结果，不提供历次成功结果列表。
- 消息审计列表只展示便于扫描的审核状态和风险等级，包括未审核、排队中、审核中、低/中/高风险、审核失败和内容变化待重审；列表不得返回或展开完整审核正文。
- 推断会话详情内联展示摘要、风险类别、审核时间、实际审核模型、服务端任务概览和诊断摘要；风险依据、证据引用、读取覆盖范围、未覆盖说明和逐次调用诊断通过独立详情弹窗查看，避免把大段审核明细直接铺在详情页。
- 手动审核和重审入口只放在推断会话详情中；消息审计列表不提供快捷触发按钮。
- 已审核会话新增请求后，保留旧审核结果但标记为“内容已变化，待重审”；系统不自动调用 AI，只有 Root 再次手动触发才更新结果。
- AI 审核调用是管理控制面内部请求，必须绕过公开 `controller.Relay` 入口，不得触发 `CaptureMessageAudit` / `FinalizeMessageAudit`，不得形成递归消息审计。
- AI 审核调用不得进入用户计费、消费日志或额度统计，不保存 Token 用量和估算成本；只允许保存任务状态、无正文错误类别和最终结构化审核结果。
- 完整审核结果可能包含敏感摘要和判断依据，必须使用消息审计密钥派生出的独立审核密钥加密保存；列表所需的风险等级、任务状态、新鲜度和审核时间可作为无正文元数据明文保存。
- 审核输入来自推断会话已保存的入站上下文；工具定义、系统/开发者指令、历史 assistant/tool 内容均作为不可信审计材料保留，但媒体二进制仍剥离，完整重复请求快照不得无脑拼接给模型。
- 审核服务必须内置任务超时和受限 Tool 参数范围；Tool 调用次数由 Root 在固定审核配置中有界设置并随任务冻结。系统不再使用独立的累计 Tool Token 或本地估算输入 Token 阈值提前终止审核；模型实际上下文溢出由所选上游返回并映射为稳定 `context_limit`。
- 虚拟文件按消息边界提供有界分片，单条超大消息继续拆成可分页读取的虚拟分片；模型通过只读 Tool 自主选择需要读取的范围，不由后端预先生成局部摘要或无脑拼接全部正文。
- 虚拟文件和 Tool 参数必须有固定范围，Tool 调用次数必须有上限。达到调用上限或上游真实上下文上限时明确失败，并保留服务端实际覆盖记录，不得静默截断后声称已审核完整会话。
- 多次压缩会话不由后端把全部历史正文直接拼成模型输入。服务端识别每个 `session_match=compressed` 压缩断点，选取该断点的 `parent_request_id`（压缩前最后一版），再加入当前会话最新请求，组成审核资料集。
- 审核资料集以只读“虚拟文件”呈现：每个压缩前快照和最新快照各自成为一个带请求 ID、时间、压缩阶段、消息数量和 Token 估算的文档；正文仍从加密消息块按需解密，不把明文写入操作系统临时文件。
- 虚拟文件之间共享的消息继续引用现有同用户去重 blob；构造审核资料集不得复制密文或新增一份完整正文存储。
- AI 初始输入只包含审核规则和文件清单，不直接包含全部正文。AI 可调用固定会话范围内的只读工具 `list_files`、`read_file`、`search_files` 和 `search_files_regex`，自行决定读取哪些文件、区间和上下文；正则搜索使用 Go RE2 在内存资料集执行，不启动系统命令或访问真实文件系统。
- 系统必须内置一套开箱即用的默认审核提示词，至少固定定义审核目标、风险分类、风险等级、输出结构、证据引用、覆盖范围说明、Tool 使用原则和提示词注入防护；管理员无需编写提示词或配置审核规则即可使用。
- 第一版不提供管理员自定义提示词或业务规则输入，只使用内置固定审核规则，避免额外配置改变安全边界、Tool 范围或结构化输出契约。
- Tool 参数必须由后端限制在本次审核资料集内，并限制游标、字面量/正则长度、单次返回量、管理员配置的总调用次数和任务超时；禁止访问其他会话、外部网络、数据库查询或任意真实文件路径。系统设置只允许 Root 配置 Tool 调用次数，必须为正整数、默认 24，不设人为固定上限；旧配置缺失该字段时按默认值归一化。Tool 返回 Token 继续计数并写入脱敏诊断，但不设置独立累计停止阈值。
- 每次审核保存一份严格脱敏的调用诊断，至少包含渠道、模型、开始/结束时间、模型调用次数、Tool 调用次数、Tool 返回 Token、是否启用文本 Tool 回退，以及每次模型调用的阶段、协议、耗时、Tool 数、HTTP 状态和稳定错误阶段。诊断不得包含消息正文、Tool 参数、模型输出、渠道密钥或上游原始错误响应；会话详情就近展示诊断摘要，完整诊断进入审核详情弹窗。
- 审核结果必须记录无正文的读取覆盖信息，包括读取过的虚拟文件、消息区间、虚拟分片游标和 Token 估算；服务端必须额外计算任务概览，包括来源数、可用来源、原消息数、虚拟分片数、覆盖来源/消息/分片、未覆盖来源和估算 Token。界面不得把选择性读取结果伪装成已完整阅读全部资料；拆分消息只有全部虚拟分片被读取时才算原消息已覆盖。
- AI 可以自主决定读取哪些虚拟文件和消息区间；审核结果必须显示实际覆盖范围，未读取内容明确标记为未覆盖，不要求每次任务读取全部资料。
- AI 输出至少应包含简短摘要、风险等级、风险类别、判断依据和审核状态；结构必须可校验，不能把无法解析的自由文本直接当成可信结论。
- 审核必须异步执行，不阻塞正常 relay、计费、消息审计 capture/finalize 或详情查询。
- 审核失败、超时、配置缺失和重复触发必须有明确状态；不得影响原始消息审计记录的可查看性。
- 审核结果必须跟随消息审计保留期清理，不得形成脱离原正文生命周期的长期明文副本。
- 每次审核在触发时固定目标最新请求和虚拟文件来源；任务执行期间新增请求不并入本次输入，而是在成功后通过目标请求差异自动显示“内容已变化，待重审”。
- 清理任务删除任一审核来源请求时，必须同步删除对应审核结果；正在执行的任务在提交结果前重新校验来源仍存在，防止清理后重新写回已过期内容的摘要。
- 管理员手动清空必须使用整表快速清理路径，目标是在常规百万级消息引用规模下数秒完成；允许清空点击附近刚写入的审计记录。定时保留期清理继续使用在线分批删除，不得改为整表清空。
- AI 调用不得把消息正文、提示词或审核输出写入普通日志；管理审计只记录任务 ID、目标审计 ID、操作者、状态和错误类别等无正文元数据。
- 前端新增文案必须覆盖 `en`、`zh`、`fr`、`ru`、`ja`、`vi` 六种语言。
- 列表和详情必须展示同一 `request_id` 当前持久化的最终模型名；异步 finalize 更新后，列表不得长期保留采集阶段旧模型。
- 失败记录在列表和详情中展示安全的失败原因：HTTP 状态、稳定 `error_code` 及其本地化说明；不得持久化或直接展示可能回显正文、密钥、URL 或上游敏感信息的原始错误消息。
- metadata-only 记录必须明确显示“正文过大，未保存正文”，并区分“规范化正文大小”和“实际存储载荷”，避免把 1 MiB 显示误解为已存密文。
- 超限降级时仍需流式计算不含明文的会话滚动 HMAC、消息数量和前缀指纹，使相同或追加上下文的 metadata-only 请求可按 exact/prefix 归入同一推断会话；不得为实现归并重新保存超限正文。
- 原 1 MiB 全量 metadata-only 降级改为分级降级：先剥离工具定义、函数定义、系统/开发者指令和媒体信息等非 AI 审核内容，再把用户可见文本按消息边界分块加密保存到可配置的更高请求总上限；只有用户文本仍超过该硬上限时才退回 metadata-only。
- 分级降级后的每个加密块仍遵守同用户 HMAC 去重、队列总字节预算和保留期清理；不得因为提高用户文本总上限而绕过 64 MiB 审计队列预算或让 relay 同步等待持久化。
- 已通过请求校验和审计上下文构造、但在渠道选择、额度、并发或上游阶段失败的请求继续保留；失败状态不能阻止其按正常会话指纹或 metadata-only 指纹归并。
- `RelayFormatOpenAIImage` 图片生成与图片编辑请求必须进入消息审计。只保存 `prompt`、模型和数量、尺寸、质量、输出格式、流式开关等明确允许的安全参数；禁止保存上传图片、mask、images、Base64、媒体 URL 原文、任意额外字段和生成结果。
- 图片请求没有文本多轮会话语义，每个请求必须生成独立 `audit_session_id`，即使同一用户重复提交完全相同的提示词也不得按 exact/prefix/compressed 归并。图片记录可触发既有 AI 审核，但结论只能覆盖已保存文本与参数，不能声称审核过实际图片内容。
- 单次 capture 必须先在请求内按 `(user_id, schema_version, content_hmac)` 去重解析 blob：批量查询已有记录、批量插入缺失记录、再批量查询最终 ID；消息 item 保持原顺序并批量写入，不能改变载荷去重统计或并发清理语义。
- 批量写入实现必须同时兼容 SQLite、MySQL 5.7.8+ 和 PostgreSQL 9.6+，并限制批次大小以避免 SQLite 参数上限；并发插入同一 blob 时必须通过唯一键幂等收敛，不能依赖数据库专属 upsert 语法。
- compressed 候选必须先用当前锚点 HMAC 和 schema version 定位同用户已有 blob ID，再从 `message_audit_items.blob_id` 反查历史请求；候选排序、唯一匹配和有序子序列确认规则保持现有行为。
- 存储统计允许使用进程内有界时效缓存以避免固定轮询反复执行全表 COUNT/SUM；缓存只覆盖昂贵的持久化统计，不得让队列长度、运行状态、启停配置等运行时字段失真。
- 消息审计列表和状态统计不自动轮询；管理员通过现有刷新按钮按需刷新，避免后台请求让表格周期性变暗和禁用交互。
- 清空审计记录时，每个请求删除批次必须同步收集其 blob 引用，并在删除 item 后仅复核这些候选 blob 是否仍被引用；任务结束只做一次兼容历史孤儿数据的兜底扫描。
- 审核渠道不支持或忽略原生函数调用时，允许自动切换到严格 JSON 文本工具协议；原生请求不得依赖兼容性差的 API 级 `tool_choice=required` 强制调用，必须由内置提示词和后端覆盖校验约束模型先读资料。模型仍只能请求固定的 `list_files`、`read_file`、`search_files`、`search_files_regex`，所有参数、范围和调用次数继续由服务端校验执行。
- 消息审计详情必须按跨协议语义展示角色：Responses `function_call` 显示为 `assistant/tool_call`、`function_call_output` 显示为 `tool/tool_result`，Claude/Gemini 的纯工具调用或纯工具结果块同样归入对应语义角色，不得因为传输协议缺少角色或使用外层 `user` 而全部显示成用户消息。该归类只影响详情和 AI 审核读取，不重写密文、原始协议载荷或会话指纹，并兼容历史记录。
- 线上运行参数应限制应用 SQL 连接池不超过 MySQL 可承受范围，并为 InnoDB 配置与数据规模匹配的 buffer pool；不通过单纯提高 `max_connections` 掩盖查询放大，也不降低事务持久性保证。

## Scope Decisions

- [x] AI 渠道与模型交互：在系统设置中配置一组全站固定的渠道和模型；审核入口不提供另一套选择交互或临时覆盖。
- [x] 上下文边界：不设置独立累计 Tool Token 或本地估算输入 Token 停止阈值；Tool 调用次数允许 Root 配置任意正整数，默认 24，模型真实上下文溢出由上游稳定归类。
- [x] 审核提示词与规则：系统提供完整默认提示词、风险分类和输出结构；第一版不提供管理员自定义提示词或业务规则配置。
- [x] 结果展示层级：消息审计列表只显示审核状态和风险等级，完整结果仅在推断会话详情中展示。
- [x] 重审结果保留：只维护最后一次成功结果；待重审、重审中或重审失败时保留并展示旧风险与结论，新结果成功后再原子替换，不提供历史版本列表。
- [x] 触发入口：只在推断会话详情中提供手动审核/重审按钮，列表不提供快捷操作。

## Acceptance Criteria

- [ ] Root 管理员可从消息审计页面触发并查看 AI 审核结果，非 Root 访问被拒绝。
- [ ] 列表只显示审核状态和风险等级；会话详情内联显示摘要、类别、审核概览、诊断摘要、审核时间和审核模型，依据、证据、读取覆盖范围、未覆盖说明和逐次调用诊断通过详情弹窗查看。
- [ ] AI 审核与重审只能从推断会话详情触发，列表不存在容易误触的快捷审核按钮。
- [ ] 系统设置支持按渠道、模型两级联动保存全站固定审核配置；审核入口不重复展示选择器，未配置或配置失效时给出前往设置的明确提示。
- [ ] AI 审核在后台执行；任务排队、运行、成功、失败和重试状态可见，重复请求不会并发生成相互覆盖的结果。
- [ ] 会话新增请求后，旧结果仍可查看但明确显示“内容已变化，待重审”，且不会自动产生新的 AI 调用。
- [ ] “待重审”与原风险等级同时展示，不能把原高/中/低风险替换成单一状态；详情明确标出旧结果对应的审核时间和内容版本。
- [ ] 审核输出采用后端校验过的结构化契约，并展示摘要、风险等级、风险类别、依据、审核时间和审核模型。
- [ ] 审核概览由服务端基于实际 Tool 覆盖生成；单条原消息被拆成多个虚拟分片时，只有全部分片已读才计入已覆盖消息数。
- [ ] 未配置自定义提示词或业务规则时，系统使用内置默认提示词即可完成审核，并返回通过后端校验的摘要、风险、证据和覆盖范围。
- [ ] 管理界面不提供自定义审核提示词入口；审计正文中的任何角色内容和提示词注入都只作为审核证据，不能覆盖内置安全指令、扩大 Tool 权限或破坏结构化输出。
- [ ] 列表、状态、普通日志和管理审计均不泄露消息正文、密文、nonce 或完整 AI 审核输入。
- [ ] 完整 AI 审核结果以独立派生密钥加密保存；数据库明文字段仅包含列表所需的风险、状态、新鲜度、模型和时间等无正文元数据。
- [ ] 审核请求不会新增消息审计、消费日志、额度扣减、Token 用量记录或成本记录，且不会因内部调用再次触发自身。
- [ ] 正文通过有界虚拟分片和只读 Tool 按需读取；达到管理员配置的 Tool 调用次数、任务超时或上游真实上下文窗口时明确失败，而不是静默丢失内容或使用与模型无关的固定 Token 阈值提前停止。
- [ ] 超过原 1 MiB 的请求优先保留有界、分块加密的用户文本并可供 AI 审核；工具定义等非审核内容不占用该保留额度，超过更高硬上限后才明确标记 metadata-only。
- [ ] 删除或过期清理消息审计时，其审核任务与结果同步删除；历史正文不存在时不能继续发起审核。
- [ ] 审核触发后新增请求不会改变本次固定资料集；成功结果立即按最新请求差异显示待重审，来源在执行期间被清理时任务不会重新写回结果。
- [ ] AI 审核失败不影响 relay、计费、审计 capture/finalize 和原详情查看。
- [ ] SQLite、MySQL 和 PostgreSQL 的模型、迁移、查询、幂等和清理行为一致。
- [ ] 后端测试覆盖 RootAuth、结构化输出校验、重复触发、失败/超时、清理联动和敏感内容不落普通日志；前端测试覆盖触发、轮询/刷新、状态展示和错误恢复。
- [ ] 同一请求在 capture 后、finalize 前后分别查询时，列表最终收敛到详情使用的模型名；桌面表格和移动列表行为一致。
- [ ] 审计详情按语义区分普通用户消息、模型 Tool Call 和 Tool Result；Responses、Claude、Gemini 的工具内容不会因协议传输角色而错误堆在 `user` 角色下，历史记录无需迁移即可正确展示。
- [ ] 失败记录显示本地化的安全原因和 HTTP 状态，不保存或泄露任意上游错误原文。
- [ ] 多条相同或前缀递增的 metadata-only 请求归为同一推断会话，但数据库仍不保存其正文或消息块。
- [ ] 已通过校验的失败请求继续保留并参与会话归并，列表可按失败状态筛选并查看安全原因。
- [ ] 图片生成与图片编辑请求进入审计并保存加密提示词和安全参数；媒体二进制、媒体地址原文、额外字段和生成结果不落库，重复图片请求保持独立会话。
- [ ] 正常重复上下文继续复用同用户加密消息块；metadata-only 列表明确区分规范化正文大小和实际已存载荷。
- [ ] 多次压缩会话的审核资料集包含每个压缩断点的压缩前最后一版和当前最新一版，虚拟文件不复制已有密文或把明文落盘。
- [ ] AI 只能通过受限只读 Tool 访问本次资料集，并在结果中展示已读取文件和消息区间；未读取内容不会被标记为已覆盖。
- [ ] 大消息请求的 capture 从逐消息查写改为有界批量查写；请求内重复 HMAC、跨请求重复 blob、消息顺序、载荷去重统计和清理行为均有回归测试保护。
- [ ] compressed 会话推断使用 blob ID 索引缩小候选范围，并保持原有压缩匹配结果；查询不再以扫描用户历史全部 message item 为前提。
- [ ] 状态接口的昂贵存储统计在缓存有效期内不会重复执行 COUNT/SUM，缓存过期后可刷新且错误不会污染既有正确值。
- [ ] Default 列表和状态统计仅手动刷新，不因后台轮询周期性变暗；点击刷新后模型 finalize 和 AI 审核状态与数据库一致。
- [ ] 原生 Tool 被上游忽略时自动使用受控文本工具协议完成同一工具循环，不扩大文件范围或预算。
- [ ] AI 可使用受限 RE2 正则在固定虚拟文件中检索；非法表达式、越权文件、超长模式和超量返回均以稳定错误拒绝，不调用操作系统 `rg` 或任何外部进程。
- [ ] 系统设置只配置 Tool 调用次数，必须为正整数、默认 24、不设人为固定上限；配置在任务触发时固化，每次结果携带剩余调用和累计 Tool Token，累计 Token 不再触发独立失败，达到配置次数、上游真实上下文或超时边界时仍明确失败。
- [ ] AI 审核区域展示当前任务的脱敏调用诊断；DeepSeek 等渠道失败至少可定位到配置、请求转换、上游 HTTP、响应转换或响应解析阶段，并显示安全的 HTTP 状态，不记录原始响应正文。
- [ ] 大批量清空过程中按请求批次定向回收候选 blob，避免清空完成后再执行数百轮全表孤儿扫描。
- [ ] 应用连接池和 MySQL buffer pool 的生产调整有明确配置、回滚和验证记录；不修改数据库耐久性参数。

## Out of Scope

- 用 AI 审核结果自动封禁用户、停用令牌或拦截在线请求。
- 将 AI 判断作为唯一合规结论；界面必须保留“辅助审核”语义。
- 单独采集当前请求的新模型响应正文、隐藏思考、流式增量或媒体二进制；客户端重新提交的历史模型回复属于入站上下文，不在此限制内。
