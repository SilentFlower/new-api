# AI 消息持久化审计任务 Brief

## 目标

为 new-api 增加默认关闭、root-only 的入站 AI 消息审计能力。系统按单次请求留痕，通过同一用户范围内的内容寻址消息块去重保存重复会话历史，并提供独立管理页面用于筛选、查看详情和异步一键清空。

## 已确认范围

- 只保存客户端入站、验证后的可见消息，不保存当前模型响应、流式增量或隐藏思考。
- 支持 OpenAI Chat Completions、OpenAI Responses（不含 Compact）、Claude Messages 和 Gemini GenerateContent。
- 不读取或依赖 session、thread、conversation 标识，也不要求客户端增加请求头。
- 图片、音频、视频、文件和 Base64 仅保存类型、MIME、大小、来源类别和摘要，不复制正文。
- 列表只返回元数据，详情打开时才读取并解密正文。
- 第一阶段不做导出、单条删除、密钥轮换、独立审计数据库或 ClickHouse 存储。

## 核心设计

- 主关系数据库新增 `MessageAuditRequest`、`MessageAuditBlob`、`MessageAuditItem`、`MessageAuditState` 四个模型，兼容 SQLite、MySQL、PostgreSQL。
- 每次请求保留独立元数据和有序消息引用；消息块按用户、规范版本和 HMAC 指纹去重，既节省重复历史空间，也保留每次请求的完整顺序。
- 使用 `MESSAGE_AUDIT_SECRET` 派生独立的 AES-256-GCM 加密密钥和 HMAC-SHA256 去重密钥；密钥缺失或不合法时禁止开启。
- 请求验证后同步生成已过滤的不可变安全快照，再非阻塞投递 `capture`；请求结束非阻塞投递轻量 `finalize`。后台单写协程批量加密、去重和持久化，失败时 fail-open，不影响 relay 或计费。
- relay/controller 只负责传递已验证 DTO 与最小请求上下文并调用 capture/finalize，保持薄层；协议解析、脱敏、队列和加密编排归 service，事务与查询归 model。
- 队列同时限制条目数与字节数；队列满、快照超限、持续写入失败或强制退出时允许少量漏记，并提供无正文的计数和请求关联告警。
- 默认保留 7 天，可配置 1-30 天。自动清理和一键清空都先推进持久化 `purge_before` 水位，防止清空前已入队的数据在任务完成后重新写回。

## 管理端

- 新增 root-only 路由 `/message-audits`，导航入口位于日志区域。
- 支持按时间、用户、令牌、模型、请求 ID、路径和最终状态筛选，条件同步到 URL。
- 桌面端使用右侧 Sheet，移动端使用全屏 Drawer；消息、工具和元数据分区展示。
- 页面顶部显示启用状态、密钥状态、保留期限、当前节点队列深度及进程启动后的成功、重试、失败、丢弃计数。
- 设置放在“系统设置 → 日志维护”；一键清空使用危险确认框、指定确认文本和现有系统任务进度展示。
- 所有新增文案覆盖 `web/default` 六种语言。

## 安全与审计不变量

- API 与页面均严格 root-only，后端 `RootAuth()` 是最终权限边界。
- 不保存请求头、Authorization、API Key、Cookie、密码或渠道密钥。
- 去重不跨用户，且使用密钥 HMAC，避免数据库泄露后进行常见提示词字典验证。
- 普通日志继续禁止正文；仅独立消息审计模块在默认关闭、加密、限期保留和 root-only 条件下作为明确例外。
- 查看详情与清空操作写入现有管理审计日志，日志只记录操作者、目标请求 ID 或清空动作及结果。
- 审计故障不得改变上游请求结果、重试、并发控制或计费行为。
- 不把协议分支或存储逻辑写入 `controller.Relay`，也不为简单参数转发增加多余中间层。

## 实施顺序

1. 增加配置、密钥派生与安全校验。
2. 增加四个数据模型、迁移、事务写入、查询和清理。
3. 实现四类协议的可见消息规范化与敏感内容过滤。
4. 接入 relay 生命周期、异步队列、批量写入、重试和优雅关闭。
5. 接入保留清理及异步一键清空系统任务。
6. 增加 root-only 管理 API 和操作审计。
7. 完成 `web/default` 消息审计页面、设置、清空交互和六语言 i18n。
8. 更新日志规范并完成后端、前端、跨数据库和手工全链路验证。

## 验证重点

- 未启用时零正文写入；启用后四类协议可按请求 ID 完整还原可见入站上下文。
- 相同用户的重复消息块只存一次，不同用户不共享；消息顺序和重复出现次数不丢失。
- 隐藏思考、认证信息和媒体二进制不进入快照、数据库、告警或管理日志。
- 列表不包含正文或密文，详情读取受 root 权限与密钥指纹校验保护。
- 队列满和数据库故障不阻塞请求；正常关闭按限定时间排空队列。
- 清空任务不暂停 relay，不误删截止时间后的请求，且旧队列数据不会重新出现。
- SQLite、MySQL、PostgreSQL 的迁移、去重、查询和清理行为一致。
- 桌面与移动端的筛选、详情、错误状态、清空进度和长文本展示可用。

## 主要风险

- 多节点密钥不一致会导致解密失败与去重分裂，部署必须先统一 `MESSAGE_AUDIT_SECRET` 再启用。
- 主库容量和写事务增加，需要依靠批处理、媒体剥离、消息去重、大小上限和短保留期控制影响。
- 清理水位与写入事务的锁顺序是防止旧数据重现的关键，不得在优化时破坏。
- 强制退出和持续故障仍可能造成少量漏记，这是第一阶段异步 fail-open 的明确取舍。
