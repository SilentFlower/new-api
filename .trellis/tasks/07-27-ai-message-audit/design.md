# AI 消息持久化审计设计

## 设计结论

采用“请求留痕、消息块去重”的两层业务结构，而不是为每个请求重复保存完整消息 JSON。

每次 API 调用是一条独立审计事件，用于关联请求 ID、用户、令牌、模型、计费结果和时间。请求正文被规范化为有序消息块；相同用户下内容完全一致的消息块只保存一次，各请求通过有序引用还原当时实际收到的上下文。第一阶段不读取、不保存也不依赖 session 标识。

## 数据关系

```text
审计请求 1 ─┬─ 顺序 1 → 消息块 A
             ├─ 顺序 2 → 消息块 B
             └─ 顺序 3 → 消息块 C
审计请求 2 ─┬─ 顺序 1 → 消息块 A
             ├─ 顺序 2 → 消息块 B
             ├─ 顺序 3 → 消息块 C
             └─ 顺序 4 → 消息块 D
```

第二次请求只新增消息块 D 和一组轻量引用，A、B、C 不重复保存。即使同一条消息在一个请求中合法出现多次，有序引用仍会保留每次出现的位置。

概念模型如下，最终字段以实现阶段读取现有模型和迁移约定后为准：

- `message_audit_requests`：请求 ID、用户、令牌、模型、路径、时间、状态、流式标志、消息数和审计写入状态。
- `message_audit_blobs`：用户 ID、规范版本、内容 HMAC、加密正文、正文类型、加密前大小和创建时间。
- `message_audit_items`：审计请求 ID、顺序号、消息块 ID、role 和内容类型。
- `message_audit_states`：单例清理水位，用于协调后台写入与保留/清空任务。

实际 Go 模型使用 `MessageAuditRequest`、`MessageAuditBlob`、`MessageAuditItem` 和 `MessageAuditState`，由 GORM 映射到主数据库。正文密文与 nonce 使用 `[]byte`，GORM 在 SQLite、MySQL、PostgreSQL 分别映射到 BLOB、LONGBLOB、BYTEA，避免 MySQL `TEXT` 的 64 KiB 限制。

第一阶段固定使用 `model.DB`，不使用 `model.LOG_DB`。原因是 `LOG_DB` 可能为 ClickHouse，而消息引用、事务去重、孤立块回收和清理水位都依赖关系数据库事务语义。

## 请求边界

第一阶段统一以一次 API 请求作为审计边界，不读取 `conversation`、`previous_response_id`、`session-id`、`thread-id` 或自定义会话标识，也不要求调用方修改请求。

这不会影响正文去重。后续请求重复携带历史消息时，相同消息块仍会复用；管理员打开任意请求详情，都能看到该次调用实际携带的完整有序上下文。代价是管理端不提供跨请求的会话聚合视图。

## 内容去重与加密

消息先转换为稳定的规范结构，过滤认证信息和媒体二进制，再计算：

```text
内容指纹 = HMAC-SHA256(去重密钥, 用户 ID + 规范版本 + 规范化消息)
```

使用 HMAC 而不是普通哈希，避免数据库泄露后通过常见提示词字典反查正文；加入用户 ID，避免跨用户暴露“是否输入过相同内容”。正文使用独立加密密钥和随机 nonce 静态加密，内容指纹与密文密钥分离。规范版本参与指纹，后续调整过滤或规范化规则时不会错误复用旧数据。

部署通过 `MESSAGE_AUDIT_SECRET` 提供主密钥。服务启动时从主密钥派生正文加密子密钥和内容去重子密钥，并保存不可逆的短密钥指纹到每个消息块，用于在密钥不一致时返回明确错误。启用设置前必须验证密钥存在且长度合格；多节点必须配置相同值。第一阶段不实现多密钥读取或在线轮换。

请求的完整性由有序引用保证。删除过期请求时先删除引用，再清理没有任何引用的消息块；仍被较新请求引用的历史消息继续保留，直到最后一个引用过期。

## 异步写入

接入遵循薄层原则。`controller.Relay` 只在现有验证和 `GenRelayInfo` 之后把已验证 DTO、请求 ID、用户、令牌、模型、路径和时间等最小上下文交给消息审计 service，并在请求结束时提交 finalize 元数据。控制器不感知各协议字段结构，不执行脱敏、序列化、HMAC、加密、去重、批处理或数据库访问；协议规范化和队列生命周期属于 service，事务与查询属于 model。

请求校验后立即按 DTO 类型创建不可变安全快照。协议适配层只保留可见的 system/developer/user/assistant/tool 内容、工具定义、工具调用和工具结果；媒体仅保留类型、MIME、大小、来源类别和 HMAC 摘要。OpenAI reasoning 字段、Claude thinking/signature、Gemini thought/thoughtSignature、Responses encrypted/reasoning 内容一律忽略。

安全快照受单请求大小上限约束，队列同时限制条目数和总字节数。超过上限时只投递元数据记录并标记正文不可用；队列无法接收时直接丢弃并增加计数，不阻塞 relay。

采集使用两类事件：

1. `capture`：验证后立即投递，包含入站快照和请求元数据。
2. `finalize`：请求结束时投递，只包含请求 ID、成功/失败、HTTP 状态、错误码、结束原因和耗时。

后台使用单写协程按队列顺序组批，在一个事务中依次处理事件，保证同一请求的 `capture` 先于 `finalize`。批次写入失败只做有限重试；失败后记录请求 ID 与计数，不输出正文。

单个采集事件的元数据、内容块和有序引用必须在同一数据库事务内完成，避免出现可查询但无法还原的半条记录。内容块使用 `(user_id, schema_version, content_hmac)` 唯一约束和 `OnConflict DoNothing` 处理并发去重，再查询实际 ID 建立有序引用。

服务启动时始终启动工作协程，使 root 可以运行时启用审计；关闭功能仅阻止新 capture，不阻止已入队事件、finalize 或保留清理。HTTP 服务优雅关闭后，主进程在数据库关闭前给工作协程限定时间排空队列。

## 清空语义

“清空审计数据”和自动保留清理复用同一种 root/system task handler。任务 payload 固化清理截止时间和来源类型，系统任务锁保证同一时刻只有一个消息审计清理任务：

- handler 先在事务中通过 `lockForUpdate(tx)` 锁定 `MessageAuditState` 单例并单调推进 `purge_before` 水位。
- 后台写入事务也先读取同一水位；`captured_at <= purge_before` 的旧 capture 直接丢弃，因此队列中的旧数据不会在清理后重新出现。
- handler 分批删除截止时间之前的请求引用和请求，再删除不再被任何引用使用的消息块。
- 截止时间之后的新请求继续入队和写入，不暂停 relay。
- 前端轮询任务进度，展示处理数量、删除数量和最终结果，并在任务运行时禁止重复启动。
- 清空操作写入现有管理日志，因此不会随着消息审计表一起被清除。

SQLite 不生成 `FOR UPDATE`，但写事务由 SQLite 串行化；MySQL/PostgreSQL 使用项目统一的 `lockForUpdate`。这种顺序保证先进入的写事务提交后再推进水位，随后会被清理任务删除；后进入的事务看到新水位并丢弃旧快照。

自动清理每天运行一次，截止时间为当前时间减去 1-30 天保留期限。审计开关关闭时仍继续调度清理。

## 管理 API

全部接口使用 `RootAuth()`：

- `GET /api/message-audit/`：分页元数据列表，支持时间、用户、令牌、模型、请求 ID、路径和状态筛选，不选择密文列。
- `GET /api/message-audit/:request_id`：读取有序引用、校验密钥指纹并逐块解密，返回规范化消息；成功或失败尝试均写现有管理审计日志，日志只包含操作者、目标请求 ID 和结果。
- `GET /api/message-audit/status`：返回启用/密钥配置状态、保留期限、当前节点队列容量与进程内计数。
- `POST /api/system-task/message-audit-cleanup`：创建截止时间为请求开始时刻的清空任务；任务查询继续复用现有 `/api/system-task/current` 和 `/api/system-task/:task_id`。

管理 API 延续项目 `{success,message,data}` 契约。列表与详情使用独立响应 DTO，确保列表类型从结构上不含密文和 nonce。

## 管理端界面

新增 root-only 独立路由 `/message-audits`，导航位置与“使用日志”“任务日志”相邻，导航项和路由 `beforeLoad` 都要求 `ROLE.SUPER_ADMIN`，但真正权限仍由后端 `RootAuth()` 保证。

页面统一展示请求列表：

- 请求列表用于精确取证，展示请求时间、请求 ID、令牌、模型、路径、状态、消息数、工具调用数、正文大小和去重节省量。
- 列表不返回正文或正文预览。
- 桌面端使用右侧 Sheet 展示详情，移动端使用全屏 Drawer。
- 请求详情按有序引用还原该次请求的完整入站上下文，因此可以直接查看模型在该次调用中收到的会话历史。
- 页面顶部使用紧凑状态栏展示启用状态、密钥配置、保留期限、当前节点队列深度以及进程启动后的成功、重试、失败和丢弃计数。

启用开关和 1-30 天保留配置作为独立区域嵌入“系统设置 → 日志维护”。审计页提供跳转设置、刷新和危险样式的清空按钮。清空确认要求输入当前语言下的指定确认文本，并复用现有系统任务进度交互。

列表基于现有 `DataTablePage`、URL 同步筛选和移动卡片模式。桌面详情使用 `Sheet`，移动端使用全屏 `Drawer`；正文只在详情打开时通过 React Query 获取，不写入 localStorage 或列表缓存预览。JSON 与长文本使用安全的 `pre`/文本节点渲染，不使用 `dangerouslySetInnerHTML`。

## 数据库兼容

第一阶段以主数据库的 SQLite、MySQL 和 PostgreSQL 为必需目标，使用 GORM 事务、批量创建和跨数据库可用的唯一约束。去重并发冲突必须以数据库唯一约束兜底，再读取已存在的消息块，不能只依赖进程内缓存。

ClickHouse 不作为第一阶段审计正文的默认存储；若后续支持，需要单独设计引用关系、TTL 与孤立内容清理，不能复用关系数据库实现假设。

## 主要取舍

- 相比整包快照，消息块去重显著减少长会话重复历史的存储，但会增加引用表行数和写入事务复杂度。
- 不处理 session 能减少协议适配、会话识别和聚合查询的复杂度，并避免把两个相似提示词的独立对话错误合并；代价是第一阶段只能按请求审查，不能直接浏览跨请求会话。
- 使用主数据库避免 ClickHouse 分支和新增连接配置，但会增加主库容量；默认 7 天保留、消息去重、媒体剥离和大小上限共同控制该影响。
- 采集与结束拆成两个异步事件，比请求结束后一次性入队多一次轻量队列操作，但避免流式请求长期持有大正文快照。
- relay/controller 使用薄层钩子会把少量上下文组装留在主链路，但能将高复杂度和高风险审计逻辑限制在独立 service/model 边界内。

## 发布与回滚

- 部署前在所有节点配置相同的 `MESSAGE_AUDIT_SECRET`，先发布代码并确认状态为“密钥已配置”，最后再由 root 开启审计。
- 数据表通过主库 AutoMigrate 创建；旧版本会忽略新增表和 Option，不影响 relay。
- 回滚前先关闭审计并等待队列排空。代码回滚后新增表可以保留；需要释放空间时应先通过清空任务删除数据，再执行数据库层面的表清理。
- 修改或遗失密钥会导致旧正文无法解密。第一阶段通过密钥指纹明确报错，不自动尝试旧密钥。
