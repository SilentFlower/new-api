# AI 消息持久化审计

## Goal

为 new-api 增加可选的 AI 消息持久化审计能力，使 root 管理员能够按用户、令牌、模型、请求 ID 和时间范围回看调用内容，辅助滥用排查、任务行为审查和事后取证，同时控制隐私泄露、存储膨胀和性能影响。

## Background

- 当前数据库消费日志记录用户、令牌、模型、Token 数量、渠道、请求 ID 和计费信息，但不保存 AI 对话正文；`model.Log.Content` 主要承载计费或错误说明（`model/log.go:62-83`、`model/log.go:331-389`）。
- 项目日志规范目前明确禁止记录请求/响应体和 AI 对话内容，因此实现前必须同步调整规范，并将消息审计设计为显式启用的独立敏感能力（`.trellis/spec/backend/logging-guidelines.md`）。
- 原始请求已经被解析为统一的 `dto.Request`，主要格式包括 OpenAI Chat、OpenAI Responses、Claude Messages 和 Gemini；可在验证后从 `relayInfo.Request` 获取请求语义（`relay/common/relay_info.go:109-216`、`dto/request_common.go:8-13`）。
- OpenAI、Claude、Gemini 的消息结构不同，并包含文本、工具调用、工具结果、图片、音频、文件和 Base64 数据，不能仅靠一个 `messages[].content` 字符串处理（`dto/openai_request.go:30-109`、`dto/openai_request.go:288-304`、`dto/openai_request.go:856-901`、`dto/claude.go:13-224`、`dto/gemini.go:14-32`）。
- `LOG_DB` 可能是主库，也可能是独立 SQLite、MySQL、PostgreSQL 或 ClickHouse；现有 `logs` 表同时服务统计、分页、导出和清理，直接把大正文写入 `logs.other` 或 `logs.content` 会放大这些路径的读写成本（`model/main.go:392-471`、`model/log.go:475-615`）。
- 现有日志列表由管理员访问，历史日志删除要求 root；敏感消息正文需要比普通日志更严格的权限和查看审计（`router/api-router.go:270-285`）。

## Requirements

- 审计功能默认关闭，必须由 root 显式启用。
- 消息正文使用主关系数据库中的独立审计模型和查询接口，不写入现有 `logs.content`、`logs.other` 或 ClickHouse 日志表。第一阶段不新增独立审计数据库连接。
- 审计记录必须关联 `request_id`、用户、令牌、模型、请求路径、时间、流式标志和最终状态，普通消费日志仍只保存轻量索引。审计最终展示的模型名必须与同请求消费日志的主模型字段使用同一归一化函数；采集阶段可暂存原始模型，结束事件在计费模型冻结后异步覆盖。
- 正文采用“请求清单 + 内容寻址消息块”去重：每次请求保留独立审计事件和有序消息引用，相同用户下规范化后完全一致的消息块只加密保存一次。后续请求携带重复历史时复用已有消息块，只为新增或变化的内容创建新块。
- 去重不能跨用户进行，不能仅使用普通明文哈希，不能因为去重而丢失消息顺序、重复出现次数、请求时点或单次请求元数据。
- 列表接口只返回元数据和安全聚合字段，不返回消息正文或正文预览；正文只能通过单条详情接口读取。
- 查看审计详情和清空审计数据的操作本身必须写入现有管理审计日志，管理日志不得包含消息正文。
- 不持久化 Authorization、渠道密钥、Cookie、密码、Webhook/OAuth 密钥等认证信息。
- 图片、音频、视频、文件和 Base64 内容默认只记录类型、大小、MIME、来源类别和内容摘要，不复制二进制正文。
- 默认保留期限为 7 天，允许 root 在 1-30 天范围内配置，并提供自动清理机制；关闭功能不能阻止已有记录按保留策略清理。
- 必须提供 root-only 的“一键清空审计数据”能力。清空通过异步系统任务执行，展示进度、删除数量和结果；任务启动时确定清理截止时间并推进持久化清理水位，新产生的审计继续写入，且截止时间之前已经入队但尚未持久化的数据不能在清理完成后重新出现。
- 采用非阻塞异步 fail-open：请求验证后立即生成过滤过媒体二进制和隐藏思考的不可变入站快照，并以非阻塞方式投递采集事件；请求结束时再非阻塞投递轻量状态事件。后台单写协程按顺序批量完成 HMAC、加密、去重、持久化和有限重试，两个事件都不等待数据库 I/O。
- relay/controller 接入必须保持薄层：只传递现有已验证 DTO 与最小请求上下文并调用审计 service，不在控制器中实现协议解析、脱敏、加密、去重、队列或数据库逻辑。
- 审计存储异常、队列条目或字节预算耗尽、快照超过大小上限或进程异常退出时，正常 relay 和计费继续执行；必须输出不含正文的请求关联告警和可观测计数。正常运行时目标是逐条记录，不主动采样。
- 第一阶段明确支持 OpenAI Chat Completions、OpenAI Responses（不含 Compact）、Claude Messages 和 Gemini GenerateContent 的入站可见消息；Realtime、Responses Compact、Alpha Search、Embedding、Rerank、图片、音频和异步任务协议不保存正文。
- 正文必须使用部署环境中的专用密钥静态加密；密钥缺失或不合法时不能启用审计。多节点部署必须使用完全相同的密钥。密钥本身不能写入数据库、日志或管理 API。
- 实现必须兼容主数据库的 SQLite、MySQL、PostgreSQL。

## Recommended Baseline

- 第一阶段采用独立的审计表/存储，保存结构化元数据与加密正文，现有消费日志仅通过 `request_id` 关联。
- 第一阶段只保存客户端入站、验证后的标准化消息，包括请求中已有的用户消息、系统消息、可见 assistant 历史、工具调用和工具结果；不保存当前请求产生的响应正文、隐藏思考、请求头和渠道密钥，媒体只保存元数据。
- 使用 `MESSAGE_AUDIT_SECRET` 派生相互隔离的 AES-256-GCM 正文密钥和 HMAC-SHA256 去重密钥；数据库保存密钥指纹用于诊断，不保存密钥。第一阶段不提供密钥轮换。
- 请求校验后同步完成协议规范化、媒体二进制过滤和隐藏思考过滤，只把受大小限制的安全快照投入同时受条目数与总字节数约束的内存队列；队列满或快照过大时不阻塞 relay。
- 后台单写协程按队列顺序批量完成内容 HMAC、AES-GCM 加密、消息块去重、采集记录写入和请求结束状态更新；写入失败进行有界次数和有界时间的内存重试，避免无限积压。
- 不读取也不依赖客户端提供的 session、thread、conversation 标识，不要求调用方新增请求头或修改客户端。服务端根据同一用户、同一协议下的有序会话消息前缀保守推断会话，并生成独立的 `audit_session_id`；无法唯一匹配时创建新会话。
- 服务正常关闭时在限定时间内排空队列；容器被强制终止、队列满或持续存储故障时允许少量审计缺失，不在第一阶段引入同步磁盘待重试队列。
- 默认保留 7 天，并允许 root 配置 1-30 天；先以完整采集为目标，再根据实际量级决定是否加入采样或对象存储。
- 第一阶段严格 root-only；后续如确有多人审计需求，再增加独立的审计查看权限资源。

## Frontend Presentation

- 在管理员导航的日志区域新增 root-only 的“消息审计”入口，使用独立路由 `/message-audits` 和独立查询接口，不作为普通使用日志的一个数据类型，避免继承“全部/仅自己”等不适合敏感审计的交互。
- 页面顶部使用紧凑状态栏展示：启用状态、密钥配置状态、保留期限、当前节点队列深度、进程启动后的成功数、重试数、丢弃数和写入失败数；不使用大面积营销式卡片。
- 状态栏同时展示当前有效密文载荷、消息审计四张表实际分配空间、请求数、唯一消息块数和引用数，便于区分仍被记录引用的数据量与数据库可复用但未返还给操作系统的表空间；数据库无法提供表级物理占用时回退为密文与 nonce 的逻辑字节并明确标记“估算”。
- 筛选区支持时间范围、用户、令牌、模型、请求 ID、请求路径和最终状态；筛选条件同步到 URL，便于管理员保留和复现排查条件。
- 页面默认按服务端推断会话展示，列出会话最新时间、用户、令牌、模型、请求路径、请求数、消息数、工具调用数、正文加密前大小、上下文压缩次数、最终状态和最新请求 ID；列表不显示任何消息正文预览。去重节省量继续保留在后端元数据中，但不占用主表列。
- 同一用户、同一协议下，若历史请求的会话消息序列是新请求的唯一最长前缀，则新请求继承其 `audit_session_id`；完全相同的消息序列标记为精确匹配，无法匹配或最长前缀落入多个不同会话时创建新会话。独立工具定义不参与前缀判断，消息内的工具调用与工具结果仍参与。
- 前缀匹配失败且新请求明显缩短时，允许通过消息 HMAC 的严格有序子序列识别客户端上下文压缩：只使用 user/assistant/tool 等会话内容作为锚点，要求较高覆盖率、多个分散锚点、旧请求后段命中和唯一最佳候选；满足条件时继承会话并标记为 `compressed`。仅有公共 developer/system 指令、低覆盖或候选歧义时必须新建会话。
- 会话归并只影响管理端聚合展示，不合并或删除底层请求记录。每个会话使用最新请求作为代表，root 可以打开会话历史查看每次调用，并继续打开任一请求详情；会话和会话内请求均按最新时间倒序排列。主表聚合显示会话内 `compressed` 续接次数，会话历史使用醒目的边界标识区分压缩前后请求链。
- 所有筛选条件必须先作用于请求集合，再在筛选结果内按 `audit_session_id` 分组；按请求 ID 精确筛选时仍能定位到对应单次请求。历史上没有会话 ID 的记录和 metadata-only 请求必须独立展示，不能错误合并。
- 点击记录后，桌面端打开右侧 Sheet，移动端打开全屏 Drawer；仅在打开详情时请求单条正文并由后端解密。详情按“消息 / 工具 / 元数据”分区，消息区使用纵向时间线展示 role、顺序和内容，媒体显示类型、大小、MIME 和摘要占位，不显示二进制内容。
- 消息区提供角色与内容类型两组多选过滤，可组合查看 user/developer/assistant 等角色，以及文本、工具调用、工具结果、媒体元数据、系统指令等当前详情实际存在的类型；默认全选，过滤仅改变当前详情展示，不修改审计数据和原始顺序。
- 请求详情严格还原该次请求当时引用的有序消息清单，同时显示当前请求的会话续接方式和该推断会话的压缩次数；详情内部提供推断会话历史选择器，管理员选择另一条请求后在当前 Sheet/Drawer 内原位刷新，以便对照压缩前后的完整上下文。
- 页面提供刷新和“清空审计数据”操作。清空按钮使用危险样式和删除图标，确认框要求输入指定确认文本，任务执行期间禁用重复提交并展示进度；清理完成后显示删除条数，并明确说明审计启用时截止点之后的新请求仍会写入、删除行不会自动收缩数据库已分配空间。
- 审计启用开关和 1-30 天保留期限配置放在“系统设置 → 日志维护”，消息审计页只显示当前配置和跳转入口，避免浏览数据时误改全局策略。
- 所有新增文案进入 `web/default` 的六语言 i18n 文件；桌面表格和移动端详情都必须支持长文本、JSON、工具参数折叠以及安全复制。

## Acceptance Criteria

- [ ] 未启用审计时不写入消息正文，relay 行为和现有日志响应不变。
- [ ] 启用后，支持的文本协议能够通过请求 ID 查询到结构化审计记录。
- [ ] OpenAI Chat、OpenAI Responses、Claude Messages 和 Gemini GenerateContent 的可见文本、工具定义、工具调用与工具结果能够规范化；媒体二进制、隐藏 reasoning/thinking、签名和加密内容不会进入快照。
- [ ] 同一用户的后续请求重复携带相同历史消息时，重复消息正文只持久化一次；每次请求仍能按当时顺序完整还原，且不同用户之间不共享去重内容。
- [ ] 第一阶段不持久化当前模型响应正文；响应侧继续使用现有消费日志记录状态、Token、耗时、结束原因和工具计数等元数据。
- [ ] 普通用户、普通管理员和未授权 API 不能读取审计正文。
- [ ] 审计列表不返回正文；详情读取会产生包含操作者和目标请求 ID 的管理审计日志。
- [ ] 新请求 finalize 后，消息审计列表、会话历史和详情中的模型名称与同请求消费日志的 `model_name` 一致；未得到最终计费模型时不得用空值覆盖采集阶段模型。
- [ ] 请求头、API Key、Cookie、密码和媒体二进制不会进入审计存储。
- [ ] 未配置合法 `MESSAGE_AUDIT_SECRET` 时后端拒绝开启审计；数据库泄露时正文不能仅凭数据库内容直接解密或通过常见提示词字典验证。
- [ ] 过期记录能够按保留期限自动删除，root 也能通过异步任务一键清空全部审计数据。
- [ ] root 能启动“一键清空审计数据”异步任务，看到进度和结果；任务不会暂停 relay，新产生的数据不被误删，清理截止时间之前的排队数据不会在任务完成后重新出现。
- [ ] 审计入队和后台写入不会等待数据库 I/O，不会导致 API 请求失败或计费遗漏。
- [ ] relay/controller 仅包含最小 capture/finalize 接入，审计业务逻辑集中在 service，数据库事务与查询集中在 model。
- [ ] 队列深度、成功数、重试数、失败数和丢弃数可观测；队列满或写入失败时能关联请求 ID 排查。
- [ ] 正常关闭会在限定时间内排空审计队列，强制退出时允许丢失尚未持久化的队列内容。
- [ ] SQLite、MySQL、PostgreSQL 上的迁移、写入、查询和清理测试通过。
- [ ] root 能从独立的“消息审计”页面按条件检索请求，列表不泄露正文，打开详情时才读取并解密正文；非 root 不显示入口且后端拒绝访问。
- [ ] 服务端不要求客户端传入会话标识，能够以唯一最长消息前缀为同一用户、同一协议的请求生成并继承 `audit_session_id`；精确重复、前缀延续、新会话和歧义分支均有明确结果。
- [ ] 客户端压缩历史后，如果新请求保留了足够多且顺序一致的旧会话内容，服务端能够以严格有序子序列识别并标记 `compressed`；只有公共指令、低覆盖或多候选时不会强行归并。
- [ ] 默认列表按推断会话展示最新请求和会话请求数；会话列表与会话内单次请求均保持最新在前，打开任一请求仍可查看独立详情。
- [ ] 主表使用专门列展示推断会话内的上下文压缩次数，不再展示去重节省列；未压缩会话显示无压缩，发生压缩时使用明显但不误导为错误的视觉标识。
- [ ] 会话历史对 `session_match=compressed` 的请求显示清晰分隔带和高亮标识；详情显示当前续接方式与会话压缩次数，并能通过内置推断会话历史选择器原位切换压缩前后请求。
- [ ] 会话归并不改变单次请求留痕、request ID 唯一性、状态、消息块去重或清理语义；历史空会话 ID 和 metadata-only 请求不会被错误合并。
- [ ] 详情消息区能按当前存在的角色和内容类型进行多选过滤，默认展示全部；组合过滤后保持原始消息顺序，并能一键恢复全部类型。
- [ ] 详情消息以可访问的纵向时间线展示，在桌面 Sheet 和移动 Drawer 中均不重叠，长文本、JSON 和工具参数可读且可复制。
- [ ] 审计设置、清空确认、任务进度、空状态、错误状态和详情视图在桌面与移动端均可用，并完成六语言 i18n。
- [ ] 状态接口和管理页面能分别展示当前有效密文载荷、审计表已分配字节与请求/消息块/引用数量；MySQL、PostgreSQL 返回表级实际分配空间，SQLite 优先使用表级页统计，无法取得时返回带估算标识的逻辑大小。

## Out of Scope

- 当前模型响应正文、流式增量和隐藏思考内容的持久化。
- 对模型输出质量、事实性或安全性的自动判定。
- 读取或依赖客户端提供的 session、thread、conversation 标识。
- 通过语义相似度、首条提示词、模型名、请求路径或单纯时间窗口进行模糊会话归属；压缩识别只允许使用精确 HMAC 有序子序列证据。
- Responses Compact、Realtime、Alpha Search、Embedding、Rerank、图片、音频和异步任务正文审计。
- 审计正文导出、单条删除、密钥轮换、独立审计数据库和 ClickHouse 审计存储。

## 变更记录

### 变更 1：服务端推断会话与详情时间线（2026-07-28）

- **原需求**：管理页面按每次 API 请求展示一条列表记录，随后曾考虑仅折叠完全相同的入站内容。
- **新需求**：由服务端按唯一最长消息前缀生成推断会话 ID，默认按会话展示并允许查看会话内全部请求；详情消息支持按内容类型多选过滤，并改为纵向时间线展示。
- **原因**：长会话每轮都会携带增长的历史内容，仅按完全相同内容无法串联同一对话；按类型过滤和时间线能降低复杂请求的审查成本。
- **影响范围**：会话前缀指纹、请求会话字段、列表分页查询与响应 DTO、会话内请求 API、详情过滤与时间线、Default 管理页面和 i18n；底层单次请求审计与消息块去重保持不变。

### 变更 2：详情筛选稳定性与清理存储语义（2026-07-28）

- **原需求**：详情提供角色与内容类型多选过滤；状态栏只展示审计表实际分配空间，清理结果只展示删除数量。
- **新需求**：Base UI 复选菜单必须放在菜单分组上下文中；状态栏同时展示当前有效密文载荷与数据库已分配空间，清理完成后明确提示新请求仍会继续写入且数据库已分配空间不会因删除行自动收缩。
- **原因**：缺少菜单分组会在生产构建触发 Base UI 错误 31；InnoDB 等数据库删除记录后会保留可复用表空间，单一“审计存储”指标会让管理员误以为清理失败。
- **影响范围**：Default 详情筛选组件、消息审计状态 DTO、存储统计查询、状态栏与清理结果文案、六语言 i18n 和相关回归测试；清理截止点、水位、异步执行与新请求保留语义不变。

### 变更 3：压缩会话可视化与详情内切换（2026-07-28）

- **原需求**：主表展示代表请求的去重节省量；会话历史仅用普通徽标显示每条请求的续接方式；打开详情后需关闭详情并重新从主表进入会话历史。
- **新需求**：主表改为聚合展示整个推断会话发生的上下文压缩次数；会话历史在 `compressed` 请求处显示明显边界并高亮该请求；详情展示当前续接方式和会话压缩次数，并提供推断会话历史选择器原位切换压缩前后请求。
- **原因**：线上会话 `audsess_fWEeMrtsmDRlUJj64bmbB24i` 在 2026-07-27 18:40:34 从 207 条消息压缩到 46 条，随后继续沿压缩后的请求链增长；代表请求通常为 `prefix`，仅看代表请求或去重节省量无法发现会话中间发生过压缩。
- **影响范围**：会话聚合查询与详情统计、请求 DTO、Default 主表、会话历史对话框、详情面板、i18n 和回归测试；会话推断算法、压缩匹配阈值和底层请求数据不变。

### 变更 4：审计模型名与消费日志对齐（2026-07-28）

- **原需求**：消息审计在入站采集时保存客户端请求的原始模型名，后续只补充状态和耗时。
- **新需求**：请求结束后使用消费日志共用的 `ConsumeLogModelName()` 异步更新审计模型名；该函数以 `BillingModelName()` 为基础并保留既有 gizmo 通配归一化，最终模型为空时保留采集阶段模型。
- **原因**：模型映射或计费模型冻结后，消费日志主模型名可能不同于原始请求模型，管理员需要通过相同请求 ID 在两个页面看到一致的模型名称。
- **影响范围**：relay 薄层 finalize 参数、消息审计轻量结束事件、模型状态更新和异步顺序回归测试；不新增迁移、不改变正文快照和主请求等待路径。
