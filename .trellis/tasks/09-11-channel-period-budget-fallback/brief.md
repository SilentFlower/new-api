# Brief — 渠道周期预算、时间规则与超限降级及 ai-fund 联动

## Goal

- 在 new-api 实现渠道周期额度、任意假期的时间规则及超限降级，并同步 `/root/project/ai-fund` 的管理和用量展示。

## Scope

- 个人与渠道池子的日、周额度；指定日期区间、每周重复时段；时段内每日上限与可选的整段合计上限。
- 永久或临时个人额度覆盖、规则预览、生效来源、剩余额度、重置时间和统计起点。
- 每个来源渠道配置一个目标渠道及模型，支持 HTTP Chat Completions、Claude Messages、Responses 的流式和非流式请求。
- 两仓管理员配置、个人状态展示及 API 联动；new-api 保存规则并统一计数。

## Non-Goals

- 严格预占、自动节假日日历、供应商账号余额、多渠道合并预算池、历史用量回填。
- 新增协议转换器、多跳降级、流中切换；WebSocket、异步任务和其他未纳入接口只执行限额检查。
- 本任务不包含线上部署、真实配置修改、提交或推送。

## Key Decisions

- 使用软限额：请求前检查已结算累计，允许在途请求结算后超额，后续请求受限。
- 按指标应用“个人明确覆盖项 > 指定日期规则 > 每周规则 > 默认配置”。未填写的项继续继承，其他个人限制及池子限制继续生效；临时覆盖到期回落当前规则。
- 时段不限定周末，可覆盖周中假期。服务端时区统一计算，日刷新不清整段额度，跨周也不清整段额度；同级同指标重叠规则拒绝保存。数值 0 表示不限，空值表示继承。
- 降级默认关闭，每请求最多一次。目标需兼容当前接口，并通过权限、能力和额度检查；使用目标模型及渠道价格计费，源额度恢复后新请求自动回归。
- 已发生上游副作用、开始输出、固定渠道绑定或存在不可迁移的上游会话引用时，不自动切换。

## Key Context

- 新策略与计数集中在独立模块，接入现有检查、结算和管理入口；保留旧个人日周计数，个人已用值的人工调整不改变池子真实消耗。
- ai-fund 通过现有池子与渠道映射调用 new-api，校验渠道映射和配置版本，避免保存到错误渠道；不保存另一份规则和计数。
- 实现遵循 SQLite、MySQL、PostgreSQL 兼容要求，保持 relaykit 独立构建，并补齐 new-api 前端七种语言。

## Risks / Deferred

- 新池子计数从上线后的结算开始，新时段计数从规则创建后开始；界面明确统计起点及覆盖范围。内存计数仅适用单实例，重启会丢失。
- 降级判断必须早于视觉辅助等外部调用，需验证 Responses 请求克隆、目标模型价格及计费状态不会沿用源渠道数据。
- Redis 已启用但不可用、策略读取失败时不能视为无限额放行。关闭新功能可回退；旧版本程序不会执行新增限制。

## Acceptance

- 个人或池子任一有效上限均能阻断；周中连续 5 天、每日 5、整段 15 时，前三天各用 5 后，第四天即使日额度刷新仍受整段限制。
- 假期默认每日 5，个人明确覆盖为 20 时采用 20，未覆盖指标和池子上限仍有效；临时到期、跨周、规则遮盖及禁用恢复均保持正确累计。
- 已用 80、上限 100 时，两个已放行的 30 可结算至 140，后续请求被限制。
- 三种 HTTP 接口均验证流式与非流式降级、目标拒绝、自动恢复及最多一次切换；仅实际执行的目标正确计费，不重复扣费或拼接回答。
- 两仓显示一致，验证配置冲突、映射变更、迟到响应、历史统计边界及个人用量调整；完成后端、前端、数据库、Redis 和 relaykit 的计划内检查。
- 两仓产品代码和上述业务验证已落地；Go 全量及 race、三库合同、Worker 582 项、React 42 项、Vue 3 项、两端构建及七语言检查已通过。详见 implement.md 的实际证据。
