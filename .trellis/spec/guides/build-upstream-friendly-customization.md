# Build 分支上游同步友好定制指南

> **最高优先级指导**：在不违反用户要求、AGENTS.md、安全契约和既有对外协议的前提下，build 分支的定制开发必须优先降低对上游代码的侵入和未来同步冲突。

## 适用范围

出现以下任一情况时，开发前必须阅读并执行本指南：

- 在 build 分支增加上游仓库没有的功能、协议、配置或界面。
- 修改 Router、Controller、Service、Model、Relay、Middleware 或前端公共入口来接入本地定制能力。
- 预计后续仍会持续同步上游提交。
- 一个方案需要“顺手重构”现有上游实现才能复用逻辑。

本指南不要求把所有代码重复一份。它要求的是：**定制业务实现独立，旧代码只保留最薄接入点；稳定公共基础设施可以复用，但不得为了复用而重构上游内部实现。**

## 决策顺序

设计 build 分支定制时，按以下顺序选择方案：

1. 新建独立文件、包、组件或目录承载完整定制逻辑。
2. 通过现有稳定扩展点接入，不修改扩展点自身语义。
3. 如果没有扩展点，在原有上游文件中加入一个最薄的条件分支、函数调用或注册项。
4. 只有独立实现无法满足明确契约时，才允许修改原有核心流程；必须在任务设计中说明原因和冲突面。

不得因为“看起来更 DRY”就抽取、改名、移动或重写上游代码。对于长期跟随上游的 build 分支，减少合并冲突优先于局部代码复用。

## 独立实现规则

- 新功能的业务状态、核心判断、协议转换、错误处理和测试优先放在新文件或新包中。
- 新模块使用清晰且可搜索的领域名称，禁止使用 `utils2`、`custom_helper` 等机械命名。
- 新模块可以调用稳定公共能力，例如 `common` JSON 包装、日志、BillingSession、DTO 接口和已有只读查询 API。
- 新模块不得要求多个原有模块同时改变内部结构来适配它。
- 不为单个定制功能搭建通用插件框架；一个窄函数调用比新抽象体系更容易同步上游。
- 为降低冲突而有意复制一小段上游流程时，必须记录“源实现、镜像实现、同步复核点”，并为两侧关键行为建立回归；不得随后又为了消除这份重复抽取通用框架。
- 配置优先进入已有扩展型 JSON 设置，但前提是字段语义确实属于该设置；不得为了避免迁移把结构化关系硬塞进无关字段。

## 最薄接入规则

原有上游文件必须尽量只承担以下一种动作：

- 注册一条路由、配置项或组件入口。
- 读取一个已解析的开关并调用新模块。
- 在既有流程的明确边界处分派到新实现。
- 将新模块返回的标准结果交回原有错误、重试或响应机制。

理想接入形态：

```go
// 原有上游文件只负责分派，完整逻辑位于新模块。
if compactpassthrough.ShouldHandle(relayInfo) {
	return compactpassthrough.Handle(c, relayInfo)
}
```

禁止把完整定制逻辑直接铺进原有大函数：

```go
// 错误：在上游核心流程中插入大量定制状态、计费和转发逻辑。
if relayInfo.IsResponsesCompact() {
	// 数十行 build 分支专用实现……
}
```

## Diff 控制

- 不修改与任务无关的格式、缩进、import 顺序、注释、命名和代码位置。
- 不在接入功能时顺手清理历史代码、统一风格或移动文件。
- 不把上游文件整体格式化；格式化范围必须限制在新增文件和实际修改区块。
- 一个原有文件出现多个分散接入点时，应重新评估能否收敛为一个入口。
- 新增测试优先放在新测试文件；只有验证既有公共契约时才修改原测试文件。
- 删除或替换上游实现必须有明确用户授权，不能以“新实现更干净”为理由自行扩大范围。

## 与代码复用规则的关系

build 分支定制下，复用优先级如下：

1. 复用稳定、公开、已有多个调用方的基础能力。
2. 复用不会要求修改旧实现的窄接口。
3. 新建独立实现，允许少量局部重复以换取清晰隔离和低冲突。
4. 禁止为了消除少量重复而抽取或改写上游核心逻辑。

当本指南与“优先复用现有业务实现”的一般建议冲突时，**build 分支上游同步友好原则优先**。

## 任务规划要求

每个 build 分支定制任务的 `design.md` 和 `implement.md` 必须列出：

- 新建文件和它们承载的完整职责。
- 必须修改的原有上游文件。
- 每个原有文件中的最薄接入点及其必要性。
- 是否复用了稳定公共能力，以及为何不会增加上游冲突面。
- 预期冲突面、回滚方式和上游同步后的复核点。

如果无法解释某个原有文件为什么必须修改，该修改不得进入实施计划。

## 检查清单

### 开发前

- [ ] 已区分新建文件与原有上游文件。
- [ ] 已搜索现有稳定扩展点，但没有为了复用而计划重构旧实现。
- [ ] 已把定制逻辑收敛到独立模块。
- [ ] 已为每个原有文件设计最薄接入点。
- [ ] 若存在有意复制，已列出源实现、镜像实现、同步字段和双侧行为测试。

### 开发后

- [ ] `git diff --stat` 中原有文件改动数量和行数保持最小。
- [ ] 每个原有文件的改动都能用一句话解释其必要性。
- [ ] 没有无关格式化、重命名、移动或注释整理。
- [ ] 删除新模块并撤销薄接入点即可回滚该功能。
- [ ] 新功能测试主要位于新测试文件，普通上游路径有明确回归保护。
- [ ] 有意复制的镜像流程已覆盖权限、选择、错误和状态初始化等全部同步复核点。

## Good / Base / Bad

- Good：新建 `compactpassthrough` 模块实现检测后的转发、计费快照和响应观测；原有 Relay 主循环只增加一次分派调用。
- Good：复用现有 BillingSession 和日志 API，但不修改它们的通用语义。
- Base：现有稳定接口已能满足需求，直接调用，不新增包装层。
- Bad：为了共用几十行逻辑重构整个 Responses handler，导致后续上游同文件更新产生大面积冲突。
- Bad：把 build 专用字段、状态和分支分散到多个上游核心文件，形成难以识别和撤销的隐式耦合。
- Bad：以“顺便优化”为由格式化或重命名未涉及的上游代码。
